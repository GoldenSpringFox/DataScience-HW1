# Task 6.3-B — Communities: color bias, granularity, and Girvan-Newman

Implementation devlog for `docs/plans/archive/6.3b-communities-next-iteration.md`, written 2026-08-12
after implementing steps 0-3 and 5 (step 4 was evaluated and not needed — see its own section
below). Companion to `docs/devlog/6.3-synergy-communities.md`, not a replacement — that entry's
history (the confound diagnosis, the metagame-broadening rebuild, the NMF pivot) is assumed, not
repeated here.

## Goal & hypothesis

Three questions raised on live review of the 6.3 notebook: (1) can the color-identity fix
(`compute_color_conditioned_tscore`, already validated for `communities.py`) be used with NMF's
soft clustering; (2) can 40 topics become meaningfully more granular, formalized rather than
guessed at; (3) is Girvan-Newman (covered in class) relevant to either. The plan's own working
hypotheses, tested here rather than assumed: symmetric NMF over the already-corrected matrix
fixes color bias; hierarchical recursion (not a wider flat sweep) fixes granularity; GN is
infeasible globally but cheap at single-topic scale.

**One hypothesis was flatly wrong, found early rather than late.** The color fix does not
propagate to topic-level purity the way expected — see Evaluation. The other two held, with the
"cheap at single-topic scale" GN claim itself needing correction (see Impediments).

## Data

Same corpus as 6.3's rebuild: 13,207 harvested decks, 18,979-card pool at `MIN_DECK_COUNT=3`.
No new harvesting in this task — every step here operates on already-ingested data via new
analysis code.

## Method & design decisions

### Step 0 — a units bug in the color-conditioned null model, found before it could bite

`compute_color_conditioned_tscore`'s null model is `expected' = N_ij · p_i · p_j` where
`p_i = weighted_marginal_i / N_i`. `weighted_marginal` already supports deck weighting
(`build_cooccurrence`'s `deck_slot_weights`), but `N_i` (`eligible_deck_count`, over
`build_color_identity_deck_counts`'s 32-row table) counted raw decks — no weighting parameter
existed. Harmless for every prior caller (`cooccurrence.py`'s own `build_and_save` never applies
deck weighting), but symmetric NMF's whole design (below) requires combining
`compute_near_uniform_weights`-weighted co-occurrence with the color correction for the first
time, and under that weighting `total_weight` (≈9,000, the sum of per-deck weights) diverges
sharply from the raw deck count (13,207). Left unfixed, `joint` scales by the weighting factor
but `expected'` doesn't, systematically under-correcting.

**Fix**: `build_color_identity_deck_counts` gained an optional `deck_slot_weights` parameter
(`edhcut/analysis/playrate.py`) — when given, sums each deck's own slot weight instead of
counting 1 per deck (column stays named `deck_count`, now float-valued rather than int).
`build_deck_color_identities` correspondingly now carries each deck's own `slot_key` (needed to
look up its weight). `eligible_deck_count`'s return type now follows the input's dtype (`int`
for the unweighted default, `float` once weighted) rather than a blanket `int()` cast, so a
weighted eligible count isn't silently truncated.

Verified with a real integration check, not just unit math: `build_color_identity_deck_counts(
deck_slot_weights=w)["deck_count"].sum()` matches `build_cooccurrence(..., deck_slot_weights=w
).total_weight` exactly (same weighted deck population, summed two different ways) — 12 new
tests in `tests/test_playrate.py`, all passing, full suite unaffected (82/82 in the touched
modules at that point).

### Step 1 — `theme_labels.py`, the measuring stick, built before any new clustering

Two label sources already in the DB: `card_tags` (`tagger_bulk`, 4,183 tags / 376,800 taggings,
fine-grained but not EDHREC-vocabulary-aligned) and `edhrec_themes` (401 rows: 270 `theme` + 131
`typal`, EDHREC's own taxonomy, but a name list with global popularity, not per-card
membership — scraping the 401 `/themes/<slug>` pages for real per-card labels is out of scope,
flagged as a user-run follow-up if wanted).

`build_theme_tag_map` bridges them: exact slug match (42/401), `typal` kind →
`typal-<singularized-slug>` (119/401, via a small irregular-plural dict — `elves→elf`,
`mice→mouse`, `fungi→fungus`, etc. — plus a generic suffix rule), and a small hand alias list
for a few close-but-not-exact `theme`-kind matches (4/401: Card Draw→`draw`, Removal→`removal`,
Ramp→`mana-producer`, Cycling→`cycle`, etc.) — **165/401 themes matched overall**. The other 236
are broad EDHREC umbrellas (Tokens, Aristocrats, Voltron, ...) with no single clean 1:1 tagger
tag; rolling those up into multi-tag unions was judged a materially bigger undertaking than "a
small alias dict" and would blur the exact resolution distinction this module exists to
measure, so left unmapped by decision, not oversight.

`build_theme_labels` produces per-card `(oracle_id, label, source, edhrec_theme)` rows: every
`card_tags` tag with 20-3,000 cards (within the analysis pool) becomes a label, renamed to its
matched theme's name where one exists (`source='theme'`), else the raw tag (`source='tag'`) —
**membership is always the tag's real membership**, never a theme-inferred one, so the label
vocabulary's size and content are fully reproducible from `card_tags` alone.

`topic_theme_enrichment` computes hypergeometric enrichment for every (topic, label) pair with
≥5 shared cards, BH-FDR corrected across the *whole* tested grid (own `_benjamini_hochberg`
implementation, standard step-up procedure), filtered to `lift ≥ 3 AND q ≤ 0.01`. Each surviving
row carries `resolution = min(share_of_topic, recall_of_label)` — the actual granularity metric
(a label "resolved" means some topic both dominates it and is dominated by it), distinct from
"covered" (enriched in ≥1 topic — recall, near-saturated, not the objective; conflating the two
would have made granularity look solved when it wasn't).

**Acceptance check: reproduced the planning session's own hand-computed baseline exactly.**
Against the saved flat NMF (k=40) build: 953-tag vocabulary, median topic color purity 66.7%
(null 23.3%), 19/15/8 topics at ≥70/80/90% purity, **74/953 resolved at τ=0.10** — every number
matched to the last digit. One deliberate deviation from the hand-computed baseline: "covered"
came out 728/953 via the module's real BH-FDR correction vs. 587/953 from the planning session's
ad hoc `p<1e-6` threshold — expected and fine, since "covered" isn't the metric anything is
optimized against; the number that had to match (resolved-at-τ=0.10) did.

### Step 2 — `symnmf_packages.py`: SymNMF over the color-conditioned matrix

**Why not patch raw-presence NMF's input directly**: a card's color-identity legality is
*structural* in the deck×card matrix — a mono-green card has literally zero support outside
green-legal decks, at any column scaling, and NMF's non-negativity forbids subtracting an
expectation. Two patches considered and rejected: per-column rescaling (can't change *where* a
column has support — mathematically incapable of removing block structure, not just impractical)
and frozen "color background" components (sound in principle, but `sklearn.decomposition.NMF`
can't freeze part of `H` — `update_H=False` freezes all of it — so it needs a custom
multiplicative-update loop regardless, at which point reusing the already-validated correction
below is both simpler and doesn't invent a second, unvalidated statistic).

**The design**: `S = max(compute_color_conditioned_tscore(...), 0)`, built from a
`compute_near_uniform_weights`-weighted `build_cooccurrence` (matching `communities.py`'s own
weighting choice — diversity of discovered packages over metagame-accurate representation) and
Step 0's now-consistent weighted eligible-deck-count math. Basics-only land exclusion
(`communities.basic_land_mask`), **not** all-lands — `nmf_packages.py`'s all-lands exclusion
fixed a raw-presence-specific failure mode (a nonbasic land's near-universal within-color-pair
presence, an easy signal for that factorization), and t-score doesn't share it (a land's
association with any *one* card stays weak in t-score, so it never concentrates on one
archetype) — re-verified live for this build (Cultivate/Kodama's Reach check, below), not
assumed by analogy. Top-50 union-symmetrized sparsification, factored out of `communities.py` as
`sparsify_top_k_union` (public) so both modules share one implementation rather than duplicating
the rule — `communities.build_graph` is now a thin wrapper around it, existing tests unaffected.

**Solver**: symmetric NMF has no `sklearn` mode, so a custom damped multiplicative-update loop
(`H *= (1-β) + β·(S@H)/(H@(HᵀH))`, `β=0.5`), never forming `H@Hᵀ` (would be `n×n` dense, ~2.7 GiB
at `n≈18,000`) — every quantity, including the Frobenius residual reported for convergence,
routes through `k×k` intermediates. `nmf_packages.py`'s `_memberships_table` and
`_match_topic_stability` were promoted to public (`memberships_table`, `match_topic_stability`)
specifically so this module reuses them verbatim rather than re-deriving the same
threshold/cap/Hungarian-matching logic a second time.

**`β=0.5` was checked live, not assumed** (a claim that started life unverified in an early
docstring draft — caught and fixed, see the note in Interesting findings below). 18 (k, seed)
combinations on the real `S` (k ∈ {15, 40, 80}, 3 seeds each): `β=1` (undamped) was monotone in
most runs but genuinely oscillated in two — k=40 seed=1: 65/149 iterations with an *increasing*
residual (up to +0.00042 in one step); k=80 seed=7: 54/149 increasing. `β=0.5` showed **zero**
residual increases across all 18 runs. Not a universal problem with `β=1` (most runs were fine
either way), but real and seed-dependent — exactly the failure a k-sweep across seeds would
otherwise silently paper over by discarding an unlucky run without anyone noticing why.

**Measured fit cost vs. the plan's own estimate — much cheaper than expected, and the sweep grid
was widened as a result.** Plan's estimate (extrapolated from raw-presence NMF's ~k^2.25 scaling
on the deck×card matrix): potentially a week of compute for a wide sweep. Measured on the real
`S` (n=18,292 after sparsification): k=15 → 3.0s, k=40 → 6.0s, k=80 → 33s, k=150 → 62s, k=300 →
143s — a fundamentally smaller, sparser problem than the deck×card matrix, not the same cost
curve extrapolated. `K_GRID` widened from a direct copy of `nmf_packages.py`'s `[15,20,25,30,40]`
to `[15,20,25,30,40,60,80]`, specifically so the sweep could see whether stability truly peaks or
was just hitting the old grid's ceiling (as happened to the flat NMF build).

### Step 3 — `symnmf_hierarchy.py`: recursive decomposition for granularity

Fit a small top-level SymNMF split (`TOP_K_HIERARCHY=10`), then for each resulting topic induce
`S` on just its own member cards and split again (`CHILD_K=6`), recursing until a node drops
below `MIN_NODE_CARDS=60`, hits `MAX_DEPTH=4`, or its own children's seed stability falls below
`MIN_CHILD_STABILITY=0.7` (an unreliable split is discarded, the node stays a leaf). Each split
reuses `memberships_table` (same threshold/cap convention as the flat build), so a card can
recurse down more than one branch when it clears threshold in multiple children — the tree is
not a strict partition, deliberately, for the same overlap reasons the whole project moved off
hard clustering.

`cut_at(nodes, n_leaves)` produces a flat-build-schema membership table for any requested
node-count, via greedy largest-first frontier expansion (repeatedly replace the biggest
expandable frontier node with its own children) — the tree is fit once, any granularity level is
then a cheap lookup, not a rebuild.

**Real build**: 2,423 nodes (2,020 leaves, 403 internal), max depth 4, built in 63s from the
already-cached `S`/pool. `granularity_curve` sweeps a cut and re-runs Step 1's two diagnostics at
each point.

## Evaluation & results

### Q1 — color bias: a genuinely surprising, honestly-reported negative result

The plan's pre-declared target was median purity ≤45% and zero topics at 100%. **Not met.**
Measured: median purity 68.3% (SymNMF) vs. 66.7% (flat NMF) — essentially unchanged, slightly
worse — and 3 topics at exactly 100% purity (vs. 2 for flat NMF).

This was investigated rather than accepted at face value, because the underlying correction is
independently validated (6.1's own 20-pair check) and a null result deserved a mechanism, not
just a number. Direct measurement: sampling 500 pool cards' top-50 color-conditioned-t-score
neighbors vs. their top-50 *pooled* (uncorrected) neighbors, mean same-color-identity share
drops from **48.3% to 44.7%** — a real, modest edge-level effect, consistent in direction with
the validated correction. It simply doesn't propagate into a comparable topic-level change.

**Best current explanation**: a substantial share of what looked like "color bias" in the flat
build was never a legality artifact — it's genuine archetype structure (Goblins really is a red
archetype), which a correction to the *co-occurrence null model* neither can nor should remove.
This is a real, if partial, answer to the question the original 6.3 devlog left explicitly
open ("is this bias or genuine synergy, not yet disentangled") — just not the clean fix the plan
hypothesized. Recorded as a finding, not patched around: pushing the correction harder to force
the pre-declared number down would mean over-correcting past what the data supports, which the
project's own standing practice treats as a mistake, not a fix.

**Regression checks (independent of the color finding, and passed cleanly)**: Ashnod's Altar
lands 63.9% in a genuine sac-outlet/aristocrats topic (Skullclamp, Zulaport Cutthroat, Pitiless
Plunderer, Viscera Seer, Blood Artist) and 10.5%/12.9% in graveyard-adjacent topics — the overlap
behavior this whole soft-clustering approach exists to preserve. Cultivate lands 37.3% in a
clean green ramp/big-creature-payoff topic (Rishkar's Expertise, Ghalta, Goreclaw, Etali) — no
color-pair-mana-base topic, confirming basics-only exclusion (vs. `nmf_packages.py`'s all-lands)
was the right call for this input, not just a plausible-sounding analogy.

### Q2 — granularity: both pre-declared targets met, once the sweep was actually widened

The plan's own stated ceiling (~400 leaves) proved conservative — resolved-label count was
still climbing there. Extended live once that became clear:

| n_leaves | resolved @ τ=0.10 | median labels/topic | median purity |
|---|---|---|---|
| 40 | 52 | 35.5 | 66.7% |
| 400 | 289 | 18.0 | 56.7% |
| 1,200 | **356** (peak) | 9.0 | 53.3% |
| 1,700 | 349 | **6.0** | 53.3% |
| 2,000 (≈1,988 actual) | 334 | 4.0 | 55.6% |

Resolved-count clears the plan's ≥250 target early (by ~n_leaves=250) and stays clear the whole
way, peaking 356/985 around n_leaves=1,200 before a gentle decline at extreme fragmentation
(very small nodes stop matching any 20-3,000-card label well — a real, sensible ceiling on how
fine `card_tags`' own granularity can resolve, not a bug). Median labels-per-topic falls
monotonically throughout and crosses the plan's ≤6 target around n_leaves≈1,700. **Both hold
simultaneously from ~1,700 leaves on** — comfortably inside a budget that only needed revising
upward once, not a fundamentally different approach.

Color purity stays in the low-to-mid 50s throughout the hierarchy — noticeably *lower* than
either flat build's ~67-68% median, a modest positive side effect of splitting into many smaller
topics (diluting whichever large, genuinely-monocolor archetypes dominate a coarser cut), though
not the main lever this step was built for.

### Q3 — Girvan-Newman: correctly ruled out globally, and also (found live) at "one topic" scale

Ruled out globally on cost grounds (`n=18,292`, `m=568,820` on this project's own graph → up to
`m·O(nm) ≈ 5.9×10^15` operations) and shape grounds (hard partition, loses the Ashnod's-Altar
overlap this whole soft-clustering approach exists to keep).

**The plan's assumption that a single topic (~300-600 cards) would make true GN cheap turned out
false, measured rather than trusted.** `community_edge_betweenness` on topic 9's real induced
subgraph (n=1,313, m=21,575) took **3,923 seconds (~65 minutes)** — topics in this build run
larger and denser than the plan assumed. Restricting to a topic's own top-150 members by weight
brought this down to a genuinely usable **10-14s** (measured across two runs) — but that
restriction has its own real consequence: selecting by weight selects for the topic's most
generically central ("hub") cards, so the resulting subgraph is one dense blob with peripheral
outliers, and GN's best cut (by `optimal_count`, 67 clusters, modularity 0.037) is one 84-card
cluster plus 66 singletons — real algorithm behavior on real (if narrowly sampled) data, not a
bug, and reported as such rather than hidden or replaced with a cleaner-looking fake example.

`community_fastgreedy` on the *full* graph — the scalable stand-in — ran in 40-47s (measured
across three runs) and surfaced a clean, directly-observed illustration of modularity's own
resolution limit: modularity rises to ~0.5135 by ~10-16 clusters, then goes **completely flat,
even dipping slightly, all the way out to 1,000 clusters**, while the largest cluster barely
shrinks (≈5,800 → ≈5,300 cards). `√(2m) ≈ 1,067` edges (Fortunato & Barthélemy's resolution-limit
bound) on this graph's `mean degree ≈ 62` gives a concrete floor consistent with exactly this
observation — independent, empirical confirmation of *why* a flat modularity- or
reconstruction-error-driven objective (Leiden, flat NMF, flat SymNMF alike) tops out well short
of real per-archetype granularity, and why recursion (a different mechanism entirely, not a
harder push on the same objective) was the right lever for Q2.

## Step 4 — anchored/semi-supervised SymNMF: evaluated, not built

The plan made this explicitly conditional: only build it if step 3's granularity curve
saturates below target. It didn't — both targets were met once the sweep was actually widened,
and the curve was still meaningfully non-flat in the region where they crossed (resolved-count
was still near its own peak, not asymptoting toward some lower ceiling). Building the anchored
extension anyway would have been solving a problem the data didn't show existing. Not attempted,
by decision, not oversight — if a future corpus/label-vocabulary change makes granularity
saturate below target again, the plan's own λ-sweep design (§Layer 3b) is still the documented
next step.

## Interesting findings

- **A claim was written into a docstring before it was verified, caught, and fixed rather than
  left standing.** An early draft of `symnmf_packages.py`'s module docstring asserted `β=0.5`
  was chosen because `β=1` was "found live" to oscillate — written before any such comparison
  had actually been run. A single quick check (k=30, seed=42) initially seemed to *contradict*
  it (both betas converged fine, undamped even faster). Rather than either quietly deleting the
  claim or leaving a false one in shipped code, ran the broader 18-combination check described
  above, which showed the original claim *was* substantively true — just not visible in one
  narrow test. The docstring now cites the real numbers instead of a vague "see the devlog for
  traces" that would have gone unfulfilled.
- **Two more real bugs, both caught by a number that didn't add up, not by a failing test**:
  (1) `theme_labels.granularity_report`'s `median_labels_per_topic` assumed `topic_id` values
  are always a contiguous `0..k-1` range (true for every flat build) and silently returned 0.0
  for any other scheme — a hierarchy cut's `topic_id` is a `node_id`, arbitrary and
  non-contiguous. Caught by noticing the hierarchy curve's own median-labels column was flatly
  0.0 at every row, an obviously-wrong result the toy fixture tests never exercised (their small
  fixtures happen to use topic ids 0 and 1). Fixed by reindexing against the membership table's
  own actual `topic_id` values, not an assumed range; regression-tested with deliberately
  non-contiguous ids (`test_granularity_report_handles_noncontiguous_topic_ids`).
  (2) `symnmf_hierarchy.cut_at` originally renormalized a card's `share` at each cut by summing
  its `weight` across every frontier node it appeared in — but `weight` values from *different*
  nodes come from *different* local SymNMF fits over different induced submatrices, with no
  shared scale; summing them isn't a measurement, it's noise. Cultivate genuinely clears its own
  membership threshold in 44 of 1,200 frontier nodes at one real cut (a widely-connected ramp
  staple, legitimately recurring down many branches) — cross-node renormalization diluted every
  one of those 44 real memberships below threshold simultaneously, and the card vanished from
  the cut's output entirely. Caught by trying to look up a specific named example in the
  notebook and getting zero rows back where five were expected, not by any passing test (the toy
  hierarchy fixtures are too small to produce 40+-way fan-out). Fixed by keeping each node's own
  already-meaningful `share` and capping fan-out to the strongest few nodes instead of summing
  across incommensurable ones; regression-tested with a hand-built multi-node fixture reproducing
  the exact failure shape (`test_cut_at_does_not_dilute_share_across_unrelated_nodes`).
- Both of these slipped past code review and the initial test suite specifically because the toy
  fixtures used for testing were small enough to never trigger the failure mode — a reminder
  that "the tests pass" and "ran it against real data and checked a specific number" are
  different levels of assurance, and this task leaned on the second whenever a number mattered.

## Impediments

- The stdout-buffering behavior of backgrounded Python processes on this platform (block-
  buffered when piped to a file, not a TTY) made several long-running diagnostic scripts appear
  silently stuck with zero output for tens of minutes, when in fact they were progressing
  normally — resolved by adding explicit `flush=True` / `python -u` for anything run in the
  background going forward, and by not trusting "no output yet" as evidence of a hang without an
  independent, bounded, foreground re-check.
- `nbconvert --execute` surfaced every notebook bug described above (the column-name collisions,
  the cut_at dilution, the GN full-topic infeasibility) that manual code review had missed —
  worth recording as a practice: a notebook this size needs to actually be executed end-to-end,
  not just read, before it's trusted.

## Notes for future work

- The color-bias question is *partially*, not *fully*, disentangled. A cleaner test than "does
  topic purity move" would need ground-truth labels for which specific cards' associations are
  legality-driven vs. genuinely synergistic — not available without new data (e.g., a synthetic
  corpus with color legality artificially randomized, decoupled from real deckbuilding choices).
- `card_tags`' coverage of EDHREC's own theme vocabulary tops out at 165/401 (mapped) even after
  the alias dict — scraping the 401 `/themes/<slug>` pages for true per-card theme labels would
  raise this substantially and is flagged, per the plan's own note, as a user-run follow-up (a
  large-ish scrape, not something to run unattended in this project's own established
  large-scrape convention).
- The granularity curve's resolved-count peak (~1,200 leaves) and its decline past that point is
  itself a measurement worth trusting over any fixed "how many leaves" rule of thumb for a future
  corpus — re-run `python -m edhcut.analysis.symnmf_hierarchy curve` and re-pick the operating
  point any time the underlying corpus changes materially, rather than hardcoding today's
  n_leaves≈1,200-1,700 sweet spot going forward.

# Task 6.2 — Card embeddings + similarity index
Date: 2026-08-07 | Status: done

## Goal & hypothesis
Give every commander-legal card a vector representation two different ways — Word2Vec over
real decklists (captures "travels together in practice") and TF-IDF+SVD over rules text
(captures "does a similar thing," including cards too rare in decks for Word2Vec to place
well) — so later phase-2/3 steps (communities, cut recommender) have a similarity index to
query. Plan's own success criterion: "Cultivate" should surface "Kodama's Reach" as a top
neighbor.

## Data
- Word2Vec trained on `deck_cards` directly: **2,215 deck sentences**, vocabulary pruned to
  cards in >=3 decks (`MIN_COUNT`, same pool threshold `cooccurrence.py` uses) — **7,537 cards**
  in the trained vocabulary.
- TF-IDF trained on `oracle_text + type_line` for every `cards.legal_commander = 1` row —
  **31,623 cards**, independent of deck presence.
- `struct_*` feature block (added mid-task per explicit user request, see Method below) built
  from `cards.mana_cost`/`cmc`/`power`/`toughness` — required adding `power`/`toughness` as new
  `cards` columns (they didn't exist before this task) and re-running the Scryfall ingest to
  backfill them (17,836/31,623 cards have a power value — non-creature permanents and lands
  correctly have `NULL`).
- **Deck corpus grew from 1,230 -> 2,215 decks between sessions** — the user's own uncapped
  Archidekt harvest (flagged as pending in the 6.1b devlog) has evidently been run. This means
  task 6.1's `cooccur_/pmi_/lift_/tscore_*.npz` matrices and `precon_card_retention` are now
  stale relative to the live `deck_cards` table — **not rebuilt as part of this task**, flagged
  for whoever picks up 6.1's matrices next.

## Method & design decisions
- **Word2Vec**: skip-gram (`sg=1`), `vector_size=64`, `window=100` (comfortably >= a full
  99-card deck), `min_count=3`, 10 epochs. Deck card order out of the DB is arbitrary, not a
  real sequence, so `ShuffledDeckCorpus` reshuffles each deck's own card list every time gensim
  iterates the corpus (once per epoch) rather than training on one fixed order — matters even
  with `window` larger than any real deck because gensim's own per-instance *dynamic* window
  (`randint(0, window)`, part of the original word2vec algorithm) means no single pass already
  sees every in-deck pair regardless of order.
- **TF-IDF + TruncatedSVD**: `TfidfVectorizer(min_df=2, stop_words="english")` -> `TruncatedSVD`
  to 64 dims, `tfidf_<i>` columns.
- **`struct_*` feature block — added after the plan's original text-only spec, per explicit user
  request mid-task.** The user asked whether mana cost / power / toughness should factor in, for
  three concrete reasons: assessing raw power level, grouping power/toughness-synergy cards, and
  representing "how committed to a color" a card is (their example: a triple-green card should
  sit further from a gold card than color-identity membership alone would suggest). Landed on:
  - Not tokenized into the TF-IDF vocabulary itself (numeric-scale tokens mixed into a
    text-frequency vocabulary produce arbitrary distances); instead concatenated as their own
    columns onto the **TF-IDF/SVD output specifically**, not Word2Vec's — oracle_text + type_line
    carry zero color/cost signal (no card's rules text reliably states its own cost), which is
    exactly the gap Word2Vec doesn't have (it implicitly encodes color identity via which decks a
    card can even appear in).
  - `struct_pip_<wubrg>` (z-scored per-color pip counts parsed from `mana_cost`, hybrid/Phyrexian
    symbols counting once per named color) directly operationalizes the "three green pips"
    example, rather than a coarser 5-way color-identity membership flag.
  - `struct_power`/`struct_toughness` (z-scored) plus `struct_has_power`/`struct_has_toughness`
    and `struct_power_is_variable`/`struct_toughness_is_variable` — kept as literal 0/1 flags,
    *not* z-scored (an early version z-scored everything including the flags, caught by a unit
    test expecting a literal `1.0` and getting `0.707`) so "is this even a creature" stays
    directly readable, and so a variable stat (`*`, `1+*`) is distinguishable from a real printed
    number rather than silently treated as equally reliable.
  - **Known simplification, not yet tuned**: concatenating a 12-column `struct_*` block onto 64
    TF-IDF/SVD dims implicitly weights a combined cosine search ~64:12 toward text content. Not
    corrected here — flagged for a future revisit if a nearest-neighbor check shows structured
    features being drowned out.

## Interesting findings
Both a decklist-co-occurrence method (Word2Vec) and a pure-rules-text method (TF-IDF) converge

## Impediments
- **gensim has no wheel for Python 3.14** (the repo's shared `venv/`) and its shipped C source
  doesn't even build from source there — confirmed live with a full Visual Studio 2022 Build
  Tools + C++ workload install (multi-GB) and a fresh Cython 3.2.9: the pre-generated
  `word2vec_inner.c` calls CPython internals (`PyLongObject.ob_digit`,
  `_PyLong_AsByteArray`'s old signature) that Python 3.14 changed. Not a missing-compiler issue,
  a genuine upstream incompatibility (gensim's own PyPI wheels stop at cp313, consistent with
  this being real). Resolved by adding a **second venv, `venv311/` at repo root** (Python 3.11,
  gensim has a normal prebuilt wheel there) — `gensim`/`scikit-learn` moved to a new
  `embeddings` extra in `pyproject.toml` rather than core dependencies, so the main `venv/`
  (used for everything else) still installs cleanly without them. `embeddings.py` imports
  gensim lazily (inside `train_word2vec`, not at module top level) so the module itself, and its
  non-Word2Vec tests, still work in the main 3.14 venv — only the 3 Word2Vec-specific tests are
  gated with `pytest.importorskip("gensim")` and actually run under `venv311`.
- Reintroduces the dual-venv setup the project explicitly reverted away from during task 5.1
  (see project memory) — that earlier case was avoidable duplication (`uv`-managed venv next to
  the shared one for no real reason); this one is a genuine environment incompatibility with no
  same-Python workaround available, a materially different situation.
- A first pass at the Word2Vec unit test (two toy "archetypes" sharing no cards, single-pair
  cosine comparison) was flaky — an 8-word toy vocabulary is too small for word2vec's negative
  sampling to behave intuitively (real corpora assume much larger vocabularies). Fixed by
  averaging over every intra-/inter-group pair instead of one pair, and using far more
  repetitions — a mechanical-correctness check, not a substitute for the real live sanity CLI
  above.

## Addendum 2 (same session): the `tfidf` space redesigned twice more, plus a shared
land/nonland category filter for both 6.1 and 6.2

The Data/Method/Evaluation sections above describe the space as first shipped. Real user testing
against the exploration notebook found three more real problems, each fixed in turn — current
state is what matters, not the history, but the reasoning is worth keeping:

1. **Round 1 — `struct_weight` scalar (superseded by round 2 below).** Live testing found
   Avacyn's Pilgrim's `tfidf` neighbors were *only* other single-`{G}` 1/1s — checked and
   confirmed: the `struct_*` block's average row norm was ~4x the `tfidf_*` block's despite far
   fewer dimensions (z-scored features carry unit-ish magnitude per dimension; TruncatedSVD's
   output decays fast across components), so a raw concatenation let mana cost/P-T dominate the
   cosine search almost entirely. Fixed by L2-normalizing each block separately per row before
   concatenating, then scaling `struct_*` by a `struct_weight=0.2` default. This measurably
   fixed the *symptom* (results diversified across colors) but not the root cause — still one
   lumped struct block, "weight" chosen from raw-magnitude ratios rather than any deliberate
   importance ranking.
2. **Round 2 — four independently-weighted blocks + a custom oracle-text tokenizer, per
   explicit user request.** Two further, real problems surfaced testing round 1's fix:
   - The user asked directly whether P/T factors in and asked for **{T}/{W}-style mana symbols
     to be tokenized** rather than silently dropped (sklearn's default token pattern requires
     2+ word characters, so a bare mana symbol like `{T}` never survives at all) — proposed
     explicit fixed weights themselves: oracle text 0.6, types 0.15, mana cost 0.15,
     power/toughness 0.1 (redistributed onto cost+types for non-creatures, which have nothing
     to weight there).
   - Investigating *why* Llanowar Elves (near-identical `{T}: Add {G}.` text to Avacyn's
     Pilgrim) ranked 496th under the old single-bag-of-words TF-IDF found the real root cause:
     oracle_text and type_line sharing one bag-of-words meant that for terse "vanilla" cards,
     whichever few tokens survive dominate the vector's direction — the shared type_line word
     "Human" mattered more than the actual mana ability, since oracle_text alone is often only
     1-2 real tokens.
   - Fixed by splitting into four independently-normalized, fixed-weight blocks: `tfidf_<i>`
     (oracle_text alone, `_ORACLE_TEXT_TOKEN_PATTERN` keeping mana symbols as literal tokens),
     `types_<i>` (type_line alone, its own separate TF-IDF+SVD), the existing mana-cost struct
     columns, and the existing power/toughness struct columns — each L2-normalized to unit
     length per row, then scaled by its fixed weight (0.6/0.15/0.15/0.1, summing to 1 every row
     regardless of creature status). `nearest_neighbors`'s `struct_weight` param removed
     entirely (no longer a single scalar to tune).
   - **Verified live**: Avacyn's Pilgrim's #1 neighbor became Gold Myr (a genuine same-color
     creature mana-dork twin) instead of an arbitrary same-cost/color match — a real
     improvement. But this immediately surfaced problem 3 below.
3. **Round 3 — shared land/nonland category filter, `edhcut/analysis/card_categories.py`,
   applied to *both* 6.1 and 6.2.** With oracle-text weighted at 0.6, a land whose ability text
   happens to be nearly identical to a creature's (`Plains`'s `({T}: Add {W}.)` vs. Avacyn's
   Pilgrim's `{T}: Add {W}.`) now scored almost as high as the genuine creature match — 14 of
   Avacyn's Pilgrim's top 15 `tfidf` neighbors were white-producing **lands**. User's own
   framing of the general problem: a Commander deck's land count is nearly fixed (~35-38 slots)
   regardless of which specific nonland cards it runs, so a land's statistical relationship to
   any one nonland card mostly reflects mana-base requirements, not a real substitution
   relationship — and this affects *every* method equally (PMI/t-score in 6.1 see a land's
   enormous, largely card-independent marginal deck-frequency; TF-IDF in 6.2 sees near-identical
   ability text). None of PMI/lift/t-score/Word2Vec/TF-IDF has any built-in notion that
   land-vs-nonland is a near-inviolable substitution boundary — that's Magic domain knowledge,
   not a statistical pattern. Fixed **once**, as a shared `same_category_mask()` utility, rather
   than separately (and inconsistently) per module:
   - `cooccurrence.build_card_index` gained an `is_land` column; `top_associated` gained
     `include_cross_category: bool = False`, filtering candidates via the shared mask before
     the existing self/zero-PMI exclusion.
   - `embeddings.load_text_corpus`/`build_and_save` carry `is_land` through to
     `embeddings.parquet`; `nearest_neighbors` gained the same `include_cross_category` param,
     filtering `scoped` down to the query's own category before building the space matrix.
   - Both CLIs gained a matching `--include-cross-category` flag.
   - **Verified live**: Avacyn's Pilgrim's `tfidf` list is now Gold Myr, Tooth of Ramos, Druid
     of the Anima, Skyshroud Elf, several artifact mana rocks/Talismans — a coherent "ramp"
     list, zero lands. For 6.1's PMI, the effect on Cultivate's own top-12 was subtle (PMI's
     existing marginal-frequency correction already suppresses most generically-popular lands
     for this particular query) but real and confirmed directly: a land
     (`Vastwood Fortification // Vastwood Thicket`) appears in the top-30 only with
     `include_cross_category=True`.

## Addendum 3 (same session): dual-faced cards, plus two housekeeping items

**Real bug found and fixed, per explicit user request to test DFC support**: `_parse_stat`
mis-flagged a dual-faced creature's power/toughness as `is_variable=True`. Root cause: DFC
stats are stored `"1 // 4"`-shaped (both faces joined, `scryfall.py`'s `_face_field`) — the old
code tried `float(raw)` (fails on the `" // "`), then fell straight to the same leading-number
regex used for genuine `*`-based stats (`"1+*"`, bare `"*"`), which happens to also match `"1 //
4"`'s leading `"1"` and returns the right *number* but the wrong *flag*. A dual-faced creature's
front-face stat is a real printed baseline, not a guess. Fixed: detect `" // "` first, parse the
front face's own number directly (not variable) unless the front face is itself unparseable
(e.g. a hypothetical `"* // 3"`), which still correctly falls through to the variable path.
Verified against real cards: Ulvenwald Captive // Ulvenwald Abomination (`"1 // 4"`/`"2 // 6"`)
and Huntmaster of the Fells (`"2 // 4"` both stats) now report `is_variable=False`. `_pip_counts`
needed no fix — already correctly sums both halves of a split card's joined mana cost (e.g.
Fire // Ice's `"{1}{R} // {1}{U}"` → R:1, U:1) since the regex scans for brace groups regardless
of where `"//"` falls. New tests cover both functions on real DFC-shaped values plus a full
`build_and_save`→`nearest_neighbors` pass with a DFC mixed into a tiny corpus (no crash, real
vector, sane top-1 match). Live data rebuilt after the fix.

**Housekeeping, unrelated to embeddings but done in the same session**:
- `edhcut/ingest/archidekt.py`'s harvest summary used to print every flagged-for-review deck's
  URL + reason, one per line — noisy on a large harvest. Now prints just the count; the full
  detail was already in the per-candidate audit log (`--log-file`), so nothing is actually lost.
- `precon_card_retention` (flagged as stale, un-rebuilt, in the previous addendum) was rebuilt
  against the corpus's continued growth — now 3,921 decks. Result: 3,243/3,921 decks matched
  some precon (up from 601/1,230), 28 (precon, commander) groups (up from 2) — a much larger,
  more diverse harvest is now surfacing far more precon matches than the original 5-slot/300-
  deck-cap corpus did.

## Addendum 4 (same session): CMC distance-sensitivity + oracle-text word order, `tfidf` weights
rebalanced a third time

Two more real problems, found by the user eyeballing Avacyn's Pilgrim's `tfidf` top-8 directly:

1. **"Mana cost isn't getting enough weight" — actually a representation bug, not just a
   weighting one.** `struct_cmc` was a single z-scored number folded into a cosine-similarity
   block. Cosine similarity is *scale-invariant along a shared direction*: two colorless cards
   at CMC 2 and CMC 5 (vectors `(2,0,0,...)`/`(5,0,0,...)` or their z-scored equivalents) score
   **perfectly** similar on that axis regardless of the actual gap, since cosine only measures
   angle, not magnitude. No amount of reweighting a single scalar like this can express
   "penalize a bigger CMC gap more" — the representation itself has to change. Fixed with
   `_cmc_bucket_vector`: mana value becomes a Gaussian bump across integer CMC buckets
   `0..CMC_BUCKET_MAX` (8, last bucket catches everything above), so cosine similarity between
   two cards' bump vectors now decays smoothly and monotonically with their CMC distance --
   verified directly: cosine between CMC-1 and CMC-6 bumps is 0.0019 (correctly ~zero). The CMC
   bucket sub-block and the 5 color-pip dimensions are independently normalized and recombined
   at a fixed internal 50/50 (`CMC_SUBWEIGHT`/`PIP_SUBWEIGHT`) before the mana-cost block's own
   outer weight applies, same reasoning as the top-level block weights one level down (9 CMC
   dims vs. 5 pip dims shouldn't matter purely by count either).
2. **Word order / ability structure — TF-IDF is bag-of-words, so it has none.** Confirmed live
   before designing a fix: Avacyn's Pilgrim's ("{T}: Add {W}.") top-8 included Undead Slayer and
   Tempered Veteran, whose text merely *contains* `{w}` and `{t}` somewhere unrelated, not as an
   actual ordered tap-for-mana ability. Also confirmed live that generic English stopword lists
   strip "when"/"whenever"/"at"/"if"/"each"/"one"/"more"/"may"/"until" -- exactly the words
   Magic's own templating uses to mark a triggered ability, a conditional, or a quantifier.
   Fixed with a custom TfidfVectorizer `analyzer` (`_oracle_text_analyzer`, replacing the
   bare `token_pattern` from Addendum 2) doing three things by hand: (a) splits each line on its
   first `:` -- Magic's own `<cost>: <effect>` template -- and tags every token `cost:<tok>` or
   `eff:<tok>`, so a `{t}` on the cost side is a *different* feature than one on the effect side;
   (b) adds adjacent-token bigrams within each cost/effect segment (never crossing the `:`),
   restoring some word-order sensitivity; (c) carves the MTG-significant words above out of the
   stopword list. Verified live: Undead Slayer/Tempered Veteran dropped to rank 422/610 (from
   top-8); Llanowar Elves (a near-identical `{T}: Add {G}.` dork) jumped from rank 496 (Addendum
   2's baseline) to 19.
3. **Weights rebalanced a third time, once both fixes above were live and *still* showed a real
   problem**: Princess Lucrezia (CMC 6, `{T}: Add {U}.`) ranked #3 for Avacyn's Pilgrim (CMC 1)
   despite the CMC-bump fix correctly scoring that pair's CMC-distance similarity near zero --
   the mana-cost block's 15% share (7.5% for the CMC sub-signal specifically) simply wasn't
   enough to override a near-perfect oracle-text match. User's own updated numbers: oracle text
   0.5, types 0.1, mana cost 0.3, power/toughness 0.1 (was 0.6/0.15/0.15/0.1). **Verified live**:
   Princess Lucrezia dropped from rank 3 to rank 90; Avacyn's Pilgrim's top-15 is now
   essentially every classic 1-mana dork across every color (Llanowar Elves #5, Gold Myr #7,
   Elvish Mystic, Fyndhorn Elves, Boreal Druid, Silver Myr, ...) -- a genuinely coherent result.
   Cultivate re-checked as a regression guard: still #1 self-match Kodama's Reach at 1.000
   similarity, surrounded by real "search for a basic land" ramp sorceries.

Process note: this addendum is the clearest example yet in this task of the "prototype → verify
live → get explicit numbers from the user → re-verify" cycle the project has used repeatedly for
metric/weighting decisions (t-score in 6.1, the struct-block redesign earlier in 6.2) -- every
one of the three weight-scheme revisions in this file was driven by a concrete, named live
example the user found, not a hypothetical concern.

## Addendum 5 (same session): the cost/effect-tagging + bigram analyzer reverted

User pushback on Addendum 4's word-order fix: forcing cost/effect tagging + bigrams onto TF-IDF
was "too naive" -- TF-IDF is bag-of-words and has no real notion of order, so building
preprocessing machinery to fake one is fighting the method rather than accepting what it is.
Separately, the hand-curated `_MTG_SIGNIFICANT_WORDS` stopword-exception list was only ever a
partial list (the user's own words) -- a curated whitelist for "words that matter in Magic
templating" can't realistically ever be complete.

**Resolution, `_oracle_text_analyzer`/`_ORACLE_TEXT_STOP_WORDS`/`_MTG_SIGNIFICANT_WORDS` removed
entirely**, `oracle_text` back to plain unigram bag-of-words (still through
`_ORACLE_TEXT_TOKEN_PATTERN`, which is unrelated to order -- it just keeps mana symbols from
being dropped as tokens entirely) -- but now with **no stopword filtering at all**
(`build_tfidf_svd` gained a `stop_words` parameter, `None` for oracle_text, `"english"`
unchanged for type_line). Answers the user's own question directly: TF-IDF's IDF term already
down-weights any word appearing in most documents automatically, which is the entire mechanism
stopword lists exist to approximate by hand -- skipping explicit filtering trades a marginally
larger vocabulary (free at this corpus size, absorbed by the SVD step regardless) for a
guarantee that no word, significant or not, ever gets silently dropped by an incomplete list.

**Live tradeoff, reported honestly rather than smoothed over**: reverting the order-forcing
mechanism does let some of Addendum 4's word-order win regress -- Undead Slayer/Tempered
Veteran (whose text merely *contains* `{w}`/`{t}` unrelated to a real tap ability) moved back up
to rank 52/94 for Avacyn's Pilgrim (from 422/932 with the analyzer), since plain unigrams
genuinely cannot distinguish a cost-role token from an effect-role one. Both remain well outside
any practical top-15 view, though, and everything else holds: Llanowar Elves rank 7, Princess
Lucrezia still correctly buried at rank 761 (the CMC-bucket + weight-rebalance fix from Addendum
4 is independent of the tokenizer choice and unaffected by this reversion). Cultivate's own
regression check unaffected: Kodama's Reach remains the #1 neighbor at 1.000 similarity,
surrounded by genuine "search for a basic land" ramp spells.

## Addendum 7 (same session, 2026-08-08): click-based interaction replaces hover, on both maps

Addendum 6's hover-based single map (Section 2 only) was superseded before this session ended —
hover couldn't show the on-map neighbor list or the bigger nearest-neighbor image row the user
wanted, and only covered `w2v`. Final design, described here since Addendum 6 above is now
historical:

- **Ranked by play rate, not raw deck count.** New `edhcut/analysis/playrate.py` (ad hoc, not a
  numbered plan task — decks running a card ÷ decks that could *legally* run it, by color
  identity; see `docs/devlog/play-rate-metric.md`) replaces `card_index.parquet`'s raw
  distinct-deck count as the top-N ranking signal for both maps (`TOP_N_CARDS=1000`, floored at
  `MIN_ELIGIBLE_DECKS=100` to avoid noisy rates from a tiny eligible pool).
- **Click, not hover**, on both Section 2 (`w2v`) and a new Section 3 (`tfidf`, all 31,623
  commander-legal cards, not just the >=3-deck `w2v` pool). A click populates three things: the
  image/info side panel beside the plot, a plain-text top-5-on-this-map neighbor list right
  below it, and a card-image row of the true top-5 nearest neighbors *overall* (unrestricted,
  computed in the map's own native space) sitting below the entire plot-and-side-panel row —
  the clicked card itself leads that row, set apart from its neighbors by a wider margin rather
  than a border.
- **Two real layout bugs found from a user screenshot and fixed**: (1) the bottom image row (6

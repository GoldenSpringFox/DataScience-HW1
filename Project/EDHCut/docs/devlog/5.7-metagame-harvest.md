# Task 5.7 — Metagame sample harvest
Date: 2026-08-09 (harvest completed 2026-08-10) | Status: done

## Goal & hypothesis

Not originally planned — born from task 6.3's confound: synergy communities over the
5-commander roster corpus recovered *the five commanders*, not card packages, because the
pooled association null model reads "both cards belong to commander X's pool" as synergy.
Broadening the corpus to ~1,000 commanders should fix this at the source (no single commander
forms a dominant block, so pooled marginals approximate real metagame frequencies), which
**supersedes stratification-by-slot as the alternative remedy**: a stratified estimator
degenerates at small per-stratum sample sizes (as `N_s → 1` the stratified expectation converges
on the observation and the statistic goes to 0), so it doesn't combine with a wide-but-shallow
sample. Stratification stays available for roster-scoped analyses, where strata are large enough
to estimate.

## Data

**Verified live (2026-08-09) before designing:**
- `edhrec.com/commanders` returns only 100 commanders (its "load more" paginates client-side),
  not 1,000. The 32 colour-identity pages are the cheaper route to breadth: 32 cached page
  fetches → ~2,900 distinct commanders with global deck counts.
- All 32 slugs resolve except `wr` — Boros is `rw` (the enemy-pair chain runs WB→BG→GU→UR→RW).
  Colourless is `colorless`; `c` 404s.
- Availability is heavily skewed: every 1-3 colour identity returns a full 100; 4-colour
  identities list only 9-45 commanders total.
- **The union of the 32 identity pages at `num_decks ≥ 2,300` is exactly 999 distinct
  commanders, zero duplicates** — an exact match for the user's own observation that the
  999th-ranked commander sits at 2,301 decks. This union *is* the global top-1000, reconstructed
  without paginating `/commanders`. **No identity is truncated**: the most any single identity
  contributes above the threshold is 50 (Five-Color) against the 100-per-page cap.

## Method & design decisions

Agreed with the user, 2026-08-09:

1. **Commander selection**: every commander with `num_decks ≥ 2,300`, no per-identity cap — 999
   commanders. An earlier draft capped at top-30/identity to force colour diversity; dropped
   once the live numbers showed the natural distribution is already balanced and the uncapped
   set is *exactly* the global top-1000.
2. **Deck allocation**: `n_s = clip(round(25·√(num_decks_s / max_num_decks)), 5, 25)`. √-share
   rather than proportional, so top commanders don't eat the whole budget and collapse tail
   coverage. Realised: 9,355 decks, mean 9.4/commander (median 8, spread 5-25), ~14,900
   requests, ≈8.3h at the 2.0s delay — sized to the user's ~8h budget.
3. **Kept the 2.0s delay** (politeness over speed, even at larger footprint).
4. **Design weights apply to every deck, roster included**: `w_s = true_share_s / sample_share_s`
   from `edhrec_num_decks`, computed at analysis time (never baked into the harvest) — each
   analysis chooses near-uniform (community detection) or true-share weighted (play-rate/
   staples). See `deck_weights.py`'s own docstring and task 6.3's devlog for the two formulas.
5. **`-updatedAt` ordering, not `-viewCount`** — verified live across 3 non-roster test
   commanders (Breya, Jarad, Thraximundar; 75 candidates each) through the real filter pipeline:

   | order | kept | rate | stale |
   |---|---|---|---|
   | `-viewCount` | 40/75 | 53.3% | 20 |
   | `-updatedAt` | 51/75 | **68.0%** | **0** |

   `-viewCount` pulls in decks that fail the staleness check; `-updatedAt` can't be stale by
   construction. Also found live: Archidekt's `orderBy` isn't server-validated — a nonsense
   value silently returns results identical to some default rather than erroring, so this
   ordering choice needed live confirmation, not just an assumption that the request succeeding
   meant it was honored.
6. **Roster commanders (Krenko/Kyler/Yenna) are not re-harvested** — they clear 2,300 and are
   already in the 999, so they keep their existing decks at full resolution and only gain an
   `edhrec_num_decks` row for weighting. Yoshimaru/Bruse Tarl/Orysa fall below threshold, no
   metagame-sample counterpart (expected — Orysa is the plan's own cold-start slot). **996
   commanders actually harvested.**

## Evaluation & results

All steps done 2026-08-09 except the harvest run itself (handed to the user, per the standing
large-harvest preference) and the matrix-scale guardrail:

1. `edhcut/ingest/edhrec_commanders.py` — new `meta_commanders` table
   (`slot_key`/`commander_oracle_id`/`partner_oracle_id`, mirroring `decks`'s own convention).
   Found live: EDHREC lists a partner-pair commander as one row, `name` = "A // B" (~4.3% of the
   pool, 43/999) — needed whole-name-first resolution to avoid colliding with a genuine DFC's
   own `" // "`-containing name. **999/999 resolved, 0 unresolved.** 16 new tests.
2. `edhcut/ingest/archidekt.py` gained `run_meta_sample()` / `--meta-sample`, reusing
   `harvest_slot` unchanged (now accepting `order_by`/`cohort`/`already_seen_source_ids`) rather
   than duplicating it. New `decks.cohort` column (`'roster'` default | `'meta_sample'`) with a
   `WHERE decks.cohort != 'roster'` upsert guard — a real collision path, not theoretical
   (several meta-sample commanders are the *other* half of an existing roster partner pair).
   Verified live end-to-end (2-commander smoke test, 50/50 kept, re-run made zero network
   requests and reported "already complete"). **Real bug caught before it could bite**: the
   first version had no roster exclusion at all and would eventually have re-harvested
   Krenko/Kyler/Yenna under `meta_sample` cohort too — fixed, covered by a dedicated regression
   test. 29 new tests.
3. `edhcut/analysis/deck_weights.py`: `compute_deck_weights(conn) -> {slot_key: weight}`.
   Verified live against partial data (5/999 slots harvested at the time): Kyler 0.0021, Yenna
   0.0051, Krenko 0.0098 (correctly heavily down-weighted) vs. Edgar Markov 0.90 / The Ur-Dragon
   0.91 (near 1, least oversampled). 7 new tests.
4. **Harvest run 2026-08-10** (user-executed): 996/996 commanders, 9,286 `meta_sample` decks +
   3,921 existing `roster` decks = **13,207 decks total**.
5. **Matrix-scale guardrail**, added before rebuilding: at ~13,300 decks the card pool was
   expected to grow from 4,798 to ~15-22k, and dense `n×n` float32 would be 900MB-2.5GB at that
   range. Audited the whole package first (not assumed) — everything already sparse except one
   real risk in `scripts/plot_matrix_overview.py`'s full-matrix heatmap. Added
   `assert_dense_matrix_safe` (2 GiB default ceiling), wired into both build pipelines + that one
   script. **This later turned out to be a false-positive tripwire once the real pool size was
   known — see `EDHCut_PLAN.md` task 6.1's own status block and `docs/devlog/6.3-synergy-
   communities.md`'s "Rebuild" section for the resolution, not repeated here.** 4 new tests.
6. Rebuild on the combined corpus (co-occurrence/t-score/communities/play-rates) and task 6.3's
   own follow-through (the near-uniform-weighting fix, NMF) are documented in
   `docs/devlog/6.3-synergy-communities.md`, not duplicated here — this devlog is scoped to the
   harvest itself.

**Expected side effect (confirmed positive)**: `playrate.py`'s documented limitation (only 7/32
colour identities had any decks) is fixed — all 32 populated post-harvest.

## Interesting findings

- The √-share allocation formula and the 999-commander selection rule both turned out to need
  *no* manual tuning once verified against live data — the "obvious" choices (uncapped
  top-num_decks, √ not proportional) matched the real distribution exactly.
- `-updatedAt` vs `-viewCount` is a case where the *a priori* reasoning (avoid netdecked bias)
  and the *measured* outcome (higher keep rate) happened to agree — not guaranteed, worth
  remembering that it isn't always this clean.

## Impediments

- Archidekt's `orderBy` param silently no-ops on an invalid value instead of erroring — a class
  of live-API behavior that can't be caught from documentation, only from sampling real
  responses (see the project's own standing "verify live before relying on it" practice).
- The meta-sample harvester's roster-exclusion bug (found via a smoke test that happened not to
  cover roster commanders) is a reminder that a smoke test's *coverage*, not just its pass/fail
  result, needs checking before trusting it cleared a given code path.

## Notes for future work

- Weights are computed at analysis time by design, never baked into the harvest — any future
  consumer needing a co-occurrence/synergy metric should decide near-uniform vs. true-share
  deliberately (see `deck_weights.py`'s docstring), not default to whichever is already wired
  into an existing call site.
- `compute_deck_weights`'s true-share weighting is still not wired into `playrate.py` itself —
  a real, named, not-yet-done follow-up.

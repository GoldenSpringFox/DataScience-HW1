# Task 5.4-B — EDHREC fetcher
Date: 2026-07-31 | Status: done

## Goal & hypothesis
Implement `edhcut/ingest/edhrec.py` per `docs/edhrec_api.md` (task 5.4-A): fetch each
configured commander slot's EDHREC page and populate `edhrec_card_stats`
(inclusion rate, synergy score, num_decks, category per card) and `edhrec_themes`
(theme name + deck count per slot). Reimplemented against our own cached/rate-limited
session rather than depending on `pyedhrec` directly, per the plan's step-B instruction.

285 `edhrec_themes` rows**, 5/5 slots succeeded with no errors.

## Method & design decisions
- **Cardlist-category precedence, explicit user decision** (flagged unresolved in 5.4-A):
  when a card appears in more than one EDHREC cardlist on the same page, the stored
  `edhrec_card_stats.category` prefers EDHREC's own editorial "notability" tags — priority
  order Game Changers > High Synergy Cards > Top Cards > New Cards — falling back to
  whichever type-based list (Creatures/Instants/...) the card is in otherwise. Presented to
  the user as a 3-way choice (editorial-first / type-first / store-all-memberships-as-JSON)
  with the tradeoffs of each; user picked editorial-first because it captures EDHREC's own
  judgment about *why* a card matters, which our existing Scryfall `type_line` can't tell us.
  The underlying `synergy`/`num_decks`/`potential_decks` numbers are identical regardless of
  which list wins — verified this holds live (Goblin Warchief's stats matched byte-for-byte
  whether read from "Creatures" or "High Synergy Cards" during 5.4-A's investigation) — so
  only the label is at stake, not the actual metrics.
- **Partner-pair slug**: `commander_slug()` formats each partner's name independently
  (`format_card_name`) then joins with a plain hyphen in alphabetical order — the format
  worked out empirically in 5.4-A, re-verified here against the live Yoshimaru + Bruse Tarl
  page (0 unresolved names, 236 card rows — a healthy, complete fetch, not a partial/broken
  one).
- **`commander_key` uses config order, not slug order** — deliberately: `slot_key_for()`
  (imported from `edhcut.ingest.archidekt`, same helper `decks.slot_key` already uses) joins
  oracle_ids in the order the commander names appear in `config.commander_slots`
  (`yoshi_id+bruse_id`), while the EDHREC URL slug is separately alphabetically sorted
  (`bruse-...+yoshi-...`). These are two independent identifiers serving different purposes
  (one a stable DB key, one a URL requirement) — no reason they need to agree, and tests
  assert this explicitly so a future refactor doesn't accidentally couple them.
- **Reused rather than duplicated**: `_parse_next_data` (the generic `__NEXT_DATA__`-script
  extraction Archidekt's search/precon fetchers already use) works unchanged for EDHREC's
  homepage build-ID discovery — same underlying Next.js SSR mechanism, confirmed in 5.4-A.
  Also reused `_resolve_local_oracle_id` (commander-name -> oracle_id, raises if the DB
  doesn't have it — a real setup error, not a routine unresolved-card case) and `slot_key_for`
  from `archidekt.py`, following the precedent `precons.py` already set for cross-module
  reuse of Archidekt's "private" (underscore-prefixed) helpers within the `ingest` package.
- **Did not copy `pyedhrec`'s rotating fake-browser User-Agent** (flagged in 5.4-A) —
  `edhcut.http.get_session("edhrec")` attaches our own identifying UA and the existing
  2s-delay/14-day-cache rate limit, same as Archidekt.
- **Page-shape validation, not silent tolerance**: `fetch_commander_data()` raises a clear
  `RuntimeError` if the response is missing `pageProps.data`, `container`, or `panels`
  entirely — per the plan's "if the page shape differs from the docs, stop and report; do not
  improvise" instruction. Doesn't raise on an *empty* cardlist/taglink list, though — a thin
  corpus (Orysa: only 7 themes) legitimately produces less data, and that's exactly the
  cold-start behavior the plan wants surfaced, not treated as an error.

## Evaluation & results
No pre-declared accuracy metric (structured-data ingest, not a modeling task) — correctness
checked via unit tests (18, all passing, `tests/test_edhrec.py`) plus a live run against the
real site and real DB:
- All 5 slots fetched successfully, 0 errors.
- `inclusion_rate` spot-checked against source data: top synergy card for one slot had
  `synergy_score = 0.7936`, `inclusion_rate = 0.8423` — both in the expected [0, 1] range,
  matching the `num_decks / potential_decks` computation from raw EDHREC fields.
- Re-running the same slot twice (both via the unit tests and manually) leaves row counts
  unchanged — confirms the delete-then-insert replace pattern doesn't duplicate.
- Orysa's markedly thinner theme count (7, vs. 22-133 for the other four slots) lines up with
  the plan's own cold-start expectation for that commander (§1: "few built decks exist...
  degrade gracefully to global signals") — a real signal in the data, not a bug.

## Interesting findings
- Both cards that failed name resolution across all 5 slots (`Orcrist, Goblin-cleaver`,
  `The Queen of Dale`) are recent Universes Beyond-adjacent prints — genuinely newer than the
  Scryfall snapshot task 5.2 ingested, not evidence of a normalize_name/matching bug. Good
  sign that the `card_names` resolution path (same one used for Archidekt banned-card
  detection) generalizes correctly to a second, structurally different source.
- The full live corpus (1,177 card-stat rows across 5 slots) is smaller than the naive
  "12 cardlists × ~10-50 cards" estimate from 5.4-A's raw exploration — expected, since the
  precedence-collapse step is specifically designed to dedupe a card that shows up in
  multiple cardlists on the same page down to one row.

## Impediments
None — the 5.4-A investigation had already surfaced and resolved the two hard problems
(undocumented partner slug format, page-shape verification) ahead of time, so implementation
went smoothly with only the category-precedence question needing a fresh decision.

## Notes for future work
- If a later task (e.g. 6.6's archetype labeling) turns out to need a card's *type*-based
  category specifically (not just its EDHREC notability tag), that information was discarded
  by the precedence collapse — it's recoverable by re-deriving from `cards.type_line`
  (Scryfall already has it), not by re-fetching EDHREC.
- Re-running `python -m edhcut.ingest.edhrec` (all slots) or with `--slot N` is safe/idempotent
  any time — 14-day cache means a re-run within that window makes zero new live requests.

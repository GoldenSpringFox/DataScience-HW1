# Task 5.4-A — EDHREC investigation
Date: 2026-07-31 | Status: done

Same go/no-go gate as 5.3-A, applied to EDHREC: terms, page mechanism, and whether `pyedhrec`
still matches the live site. Technical detail lives in `docs/edhrec_api.md`.

## Decisions
- **ToS conflict escalated again, and deliberately not resolved by analogy to Archidekt.**
  EDHREC's §3.1 bans automated queries, and unlike Archidekt there is *no* on-the-record
  statement welcoming third-party use — only a long-tolerated ecosystem of unofficial tools.
  Surfaced the weaker evidence explicitly; the user decided to proceed after weighing the
  actual footprint (five cached one-time fetches per refresh, never touched at runtime)
  against the high-volume use the clause targets.
- **Do not copy `pyedhrec`'s rotating fake-browser User-Agent.** It spoofs real browsers; our
  fetcher identifies itself, same as Archidekt's.
- Partner-pair slugs are each partner's slug formatted independently and joined with a hyphen
  in alphabetical order — undocumented anywhere, reverse-engineered from `/partners/<slug>`.

## Outcome
Done, go. Two constraints handed to 5.4-B: EDHREC card entries carry no `oracle_id` (only a
name/slug), so ingestion needs the `card_names` resolution path — the opposite of Archidekt's
shortcut; and a card can appear in several cardlists on one page, which collides with
`edhrec_card_stats`'s primary key. The precedence rule was left open rather than guessed.

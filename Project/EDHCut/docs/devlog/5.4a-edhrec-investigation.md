# Task 5.4-A — EDHREC investigation
Date: 2026-07-31 | Status: done

## Goal & hypothesis
Same gate task 5.3-A applied to Archidekt: before writing any EDHREC fetcher code, check
whether `robots.txt`/ToS actually permit it, and confirm the real technical shape of the
commander-page data route (build-ID discovery, card stats, themes) plus whether `pyedhrec`'s
parsing still matches the live site. Per the plan and prior session's own guidance, explicitly
did **not** assume Archidekt's welcoming outcome would generalize.

## Data
No bulk data pulled (legal/API investigation task, not ingest). Touched: `edhrec.com/robots.txt`,
`/terms` ToS, `/faq`, the homepage (for build-ID discovery), one commander page
("Krenko, Mob Boss") and one partner-pair page (Yoshimaru, Ever Faithful + Bruse Tarl, Boorish
Herder), plus a live web search for any EDHREC statement on third-party/automated use.
`pyedhrec` installed in a throwaway scratch venv (not the shared repo venv — it's not an
`edhcut` dependency).

## Method & design decisions
- **ToS conflict, not silently resolved** — same shape as Archidekt: `robots.txt` permissive,
  ToS §3.1 bans "automated...requests, or queries" verbatim. Stopped and presented this to the
  user with explicit options rather than assuming the Archidekt precedent carried over.
- **Searched for an EDHREC-specific resolving signal, found a weaker one than Archidekt's.**
  Archidekt had an on-the-record founder statement explicitly welcoming third-party use.
  EDHREC has no equivalent — checked the FAQ (only describes EDHREC *itself* pulling from
  Archidekt/Moxfield/Scryfall, says nothing about others pulling from EDHREC) and searched
  broadly for any official statement. What exists instead is a large, long-running ecosystem
  of unofficial tools (`pyedhrec` plus several independent GitHub scrapers) built on the same
  undocumented endpoints, openly documented for years with no apparent pushback — a tolerated
  norm, not a stated permission.
- **User asked what the actual use case even is before deciding** — walked through the plan's
  concrete downstream usage (archetype-cluster labeling in 6.6, two of five cut-recommender
  signals, "missing staples" suggestions, and — importantly — the evaluation baseline our own
  model needs to beat) and the footprint (5 one-time page fetches per pipeline refresh, cached
  14 days, never touched at runtime). **User then explicitly decided to proceed** on the basis
  that the footprint is tiny and clearly distinguishable from the volume the ToS clause is
  aimed at — a distinct decision from "assume it's fine because Archidekt was," made with the
  weaker-evidence situation on the table.
- **Verified rather than assumed pyedhrec still works**: didn't trust the library's age (no
  commits since 2024-02) at face value — tested `get_build_id()`, `get_commander_data()`,
  `get_commander_cards()`, `get_high_synergy_cards()` live for both a single commander and a
  partner pair.
- **Partner-pair slug format wasn't documented anywhere and had to be worked out empirically.**
  `pyedhrec.format_card_name()` has no special handling for a two-name string — naively
  formatting `"Yoshimaru, Ever Faithful + Bruse Tarl, Boorish Herder"` produces a slug with a
  literal `+` in it, which 404s. Found the real mechanism by fetching
  `edhrec.com/partners/yoshimaru-ever-faithful` (lists partner options with implied combined
  page links) and testing the constructed URL directly — confirmed the correct format is each
  partner's slug formatted independently, then joined with a plain hyphen in alphabetical
  order (`bruse-tarl-boorish-herder-yoshimaru-ever-faithful`).

## Evaluation & results
No pre-declared metric (go/no-go + technical-discovery task). Checks performed:
- `robots.txt`: fetched and confirmed no overlap with commander pages or `/_next/data/...`.
- ToS §3.1: fetched and quoted verbatim.
- FAQ: fetched, confirmed it doesn't address third-party programmatic access either way.
- Live web search for any EDHREC team statement on scraping/API/third-party tools: none found.
- `get_commander_data("Krenko, Mob Boss")`: returned the expected top-level key set
  (`creature`/`instant`/.../`container`/`panels`/etc.), `container.json_dict.card.num_decks`
  = 42,669, matching `potential_decks` on sampled card entries — confirmed internally
  consistent.
- `get_commander_cards()` / `get_high_synergy_cards()` for Krenko: returned all expected
  cardlist categories with correctly shaped entries (`synergy`, `num_decks`,
  `potential_decks`, etc.).
- Same two calls repeated for the constructed partner-pair slug: succeeded, returned a
  structurally identical payload (`num_decks` = 222 for the pair, `planeswalkers` cardlist
  present in addition to Krenko's set — confirms the cardlist tag set isn't fixed, it depends
  on what's actually populated for that slot).
- `panels.taglinks` / `tag_counts` inspected directly for both test cases — confirmed the
  `{slug, value, count}` shape needed for `edhrec_themes`.

## Interesting findings
- `pyedhrec` deliberately rotates through a static list of spoofed real-browser User-Agent
  strings (`pyedhrec/utils.py::get_random_ua`) rather than identifying itself — the opposite
  of the plan's stated posture for our own fetcher (identifying UA). 5.4-B should not copy
  this; it's a meaningful behavioral difference between "here's a library that happens to
  work" and "here's what we should actually ship."
- Card entries in EDHREC's cardlists carry no Scryfall `oracle_id` at all — only EDHREC's own
  UUID plus `name`/`slug`. This is the opposite of Archidekt's `oracleCard.uid` shortcut
  (5.3-A) — EDHREC ingestion needs the `card_names` resolution path, same as any free-text
  source, not a direct ID lookup.
- A card routinely appears in more than one cardlist on the same commander page (e.g. both
  `"highsynergycards"` and `"creatures"`), which conflicts with `edhrec_card_stats`'s
  `(commander_key, oracle_id)` primary key — 5.4-B needs a precedence rule for which
  cardlist's category/synergy value wins per card. Deliberately left unresolved here rather
  than guessing, per the plan's "if the page shape differs from the docs, stop and report;
  do not improvise" instruction extended to this adjacent ambiguity.

## Impediments
- The EDHREC-specific legal signal came out meaningfully weaker than Archidekt's — no founder
  statement, just an unchallenged tool ecosystem. Rather than treating "well, Archidekt worked
  out" as a template to reapply, surfaced the gap explicitly and let the user weigh it with
  the actual downstream use case in view (which turned out to matter — the footprint being
  five cached one-time fetches, not a live/high-volume harvest like Archidekt's 1,230-deck
  pull, was the deciding factor once stated plainly).
- No documented reference for the partner-pair URL slug format existed anywhere (not in
  `pyedhrec`, not in any of the other tools found) — had to reverse-engineer it from the
  `/partners/<slug>` listing page rather than from any written source.

## Notes for future work
- 5.4-B: resolve the multi-cardlist-per-card precedence question before writing
  `edhrec_card_stats` rows — don't default to "last write wins" silently.
- 5.4-B: build partner slugs as `"-".join(sorted(format_card_name(n) for n in partner_names))` —
  verified against the one real pair we have (Yoshimaru + Bruse Tarl); worth a second spot
  check against a differently-ordered pair once 5.4-B is live, since this was only confirmed
  with one example.
- Revisit this legal posture if EDHREC ever states anything more specific (either direction) —
  same standing rule as Archidekt's in `docs/archidekt_api.md` §1.

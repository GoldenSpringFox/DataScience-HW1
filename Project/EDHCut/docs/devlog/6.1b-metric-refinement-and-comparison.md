# Task 6.1b — Metric refinement, precon-weighting redesign, and cross-notebook comparison
Date: 2026-08-06/07 (two-session arc) | Status: done

## Goal & hypothesis
Ad hoc follow-on to task 6.1, not a numbered plan task — started from a routine notebook
card-image lookup that surfaced a real card-identity bug, and grew into: fixing that bug and
its downstream impact, redesigning the precon-contamination weighting scheme per user feedback
on how it should scope its own evidence, adding a fourth association metric (t-score) meant to
avoid PMI/lift's small-sample bias, and building a set of comparison notebooks to validate and
communicate the real differences between co-occurrence/PMI/lift/t-score before picking one to
carry forward. Hypothesis going in: PMI's own low-count discount (added in 6.1) might already
be "enough" — turned out not to be, which is most of why this step exists.

## Method & design decisions

**1. `card_names` alias-collision bug, found via a notebook image lookup, not a test.**
`edhcut/ingest/scryfall.py`'s old alias-building loop treated a card's full name and each of
its individual face names as equal, last-write-wins entries in one flat dict — whichever card
came later in the Scryfall bulk file could silently steal an alias from an earlier, unrelated
card with the same face name. Found live: `Emeritus of Truce // Swords to Plowshares` (a
`layout: "prepare"` card — a new mechanic where a creature "prepares" and lets you cast a copy
of an attached spell) has a face literally named "Swords to Plowshares," identical to the real
classic instant — its alias had completely stolen `card_names`'s only row for that name,
leaving the real card with **zero** resolvable rows. Enumerated all 55 `layout="prepare"` cards
directly against the bulk file: 19 have a spell face matching a separate real standalone card,
and 8 of those (Lightning Bolt, Swords to Plowshares, Wheel of Fortune, Demonic Tutor,
Brainstorm, Careful Study, Secret Rendezvous, Raise Dead) were actually broken under the old
logic — the other 11 happened to resolve correctly by bulk-file-order luck, not by design.
**Fix**: `build_name_aliases()` — a card's own full name is claimed in one pass first, then
face-name aliases only fill in keys nothing has already claimed, so a card's own identity
always wins over another card's incidental face-name reference to it, deterministically. Audited
downstream impact: `edhrec.py` resolves free-text names through this same table (Archidekt
doesn't — it uses Scryfall `oracle_id`s directly, unaffected); reconstructing what the *old*
buggy resolution would have produced and diffing against the fixed table found **7
`edhrec_card_stats` rows across 4 slots** holding the wrong oracle_id, with the real staples'
correct rows completely absent (not duplicated) — fixed by re-running the fetcher live.

**2. Precon-card weighting, redesigned twice** (task 6.1's original whole-*deck* novelty weight
was already fully replaced before this arc started — see `project_edhcut_implementation`
memory for that history; only rounds 1-2 below happened in this arc):
- *Round 1* (per-card, still deck-uniform trust): only cards that shipped with a deck's matched
  precon get down-weighted at all; weight is `precon_card_weight(cut_rate)` (full weight at a
  low aggregate cut rate, decaying to 0 at 100%), itself scaled by how much of the precon *that
  specific deck* still overlaps with.
- *Round 2*, user-driven refinement after a concrete counter-example (`Dearly Departed`, cut
  rate 79.6%, getting weight ~0.35 in a near-exact-copy Kyler deck but a full 1.0 in a
  heavily-rebuilt one — the motivating case): (a) the trust concept must *also* gate
  `precon_retention.py`'s own `weighted_cut`/`weighted_kept` aggregation, not just
  `cooccurrence.py`'s consumption of it — previously any deck matching a precon contributed a
  full 1.0 of evidence regardless of how unrelated it actually looked; (b) trust ceiling moved
  to "up to 10 different cards" (not only a literal exact copy); (c) the "20 shared cards"
  floor made genuinely quantity-aware (stacked basics count, not just distinct oracle_ids); (d)
  `PRECON_CUT_RATE_FULL_WEIGHT` lowered 0.40 → 0.05 (kept 95%+ of the time now required for
  full weight, not 60%+) after eyeballing the real Kyler nonland cut-rate distribution.
  `deck_precon_trust()` moved to `precon_retention.py` (avoids a circular import with
  `cooccurrence.py`, which already imports `best_matching_precon` from there) and is now defined
  purely in terms of `(diff, deck_total)` — `diff <= 10` → trust 1.0, `diff >= deck_total - 20`
  → trust 0.0, linear between.

**3. T-score, a fourth association metric**, prototyped in a scratch notebook then promoted to
`compute_tscore()` in `edhcut/analysis/cooccurrence.py`: `(joint - expected) / sqrt(joint)`,
same `MIN_PAIR_COUNT` mask as PMI/lift, no smoothing constant and no discount factor —
`sqrt(joint)` alone provides low-count damping natively. Framing (from the user): a metric that
answers "is this pairing well-*evidenced*," not just "how much more than chance" — rewarding
*both* a real gap above chance *and* enough volume behind it, deliberately trading precision for
robustness against small-sample coincidence.

**4. Notebook-comparison methodology**: rather than argue for t-score in the abstract, built
concrete, re-executed, real-number comparisons — `notebooks/cooccurrence_metrics.ipynb` gained
a full parallel "section 4" for t-score (matching co-occurrence/PMI/lift's existing heatmap
treatment) and a three-card walkthrough (Sol Ring and Moorland Rescuer, both kyler-scope; and
Cultivate, global scope) run through all four metrics side by side, plus a section reproducing
an [EDHREC video's](https://www.youtube.com/watch?v=b6Z6Pp3bz9E) lift-vs-synergy scatter plot
using lift-vs-t-score in its place, over all 61,030 kyler-scope pairs.

**5. `notebooks/my_kyler_deck.ipynb`** (new): the user's own real Kyler decklist
(`data/fixtures/my_decks/kyler.txt`, 93 distinct cards / 99 physical) compared card-by-card
against the corpus — `deck_count` (direct SQL, exact, not scoped to any co-occurrence pool
threshold), `in_precon`, `synergizes_with`/`%over_baseline`/`pair_count` (highest-lift partner,
**land/nonland-matched**: a land only suggests another land and vice versa unless the
cross-type lift exceeds 5), plus highlight sections (cards with zero other Kyler decks running
them; confirmed synergy pairs where the suggested partner is also in the deck) and a popularity
bar chart colored by `in_precon`.

**6. `edhcut/ingest/archidekt.py --max-decks`**: small CLI/`run()` override so a slot can be
harvested past the default 300-decks-per-slot cap — `search_deck_listings()` already terminates
naturally once Archidekt's own results run dry, so a large override value (e.g. 100,000) is
safe and doesn't over-fetch. 185/185 tests still pass.

## Evaluation & results
Criteria: (1) does the alias fix change resolution for the cards it should, and nothing else
(row-count and unresolved-name-count parity check before/after); (2) does t-score visibly avoid
PMI/lift's small-sample pathology on real cards, not just in aggregate statistics; (3) how
strongly do lift and t-score actually agree/disagree, quantified, not just eyeballed.

- **Alias fix**: `edhrec_card_stats` total row count (1,177) and unresolved-name count (2,
  pre-existing data-freshness gap) unchanged after the fix — confirms nothing else moved besides
  the 7 targeted rows.
- **Lift vs. t-score, all 61,030 kyler-scope pairs**: Spearman ρ = **0.959**. Every pair falls on
  the same side of both reference lines (`lift>1` iff `t-score>0`) or exactly on the boundary
  (129 pairs at `t-score=0, lift=1` exactly) — algebraically guaranteed, since both conditions
  test `joint > expected`. What differs is *magnitude*: for a fixed t-score near 0, lift's range
  spans more than an order of magnitude — the small-sample-noise effect made visible in
  aggregate across the whole scope.
- **Card-level popularity/partner anti-correlation** (separate check, motivated by a user
  observation that lift tends to pair obscure cards with obscure cards and vice versa): across a
  400-card sample of the kyler-scope pool, a card's own popularity and its lift-argmax partner's
  popularity correlate at Spearman ρ = **-0.816**.
- **Does PMI fix the small-sample bias?** No — checked directly. Sol Ring's actual PMI-argmax
  partner (kyler scope) is `Virtue of Loyalty // Ardenvale Fealty`, *more* obscure than lift's
  own top picks, not less. PMI's low-count discount (added in 6.1) only fixes one specific
  pathology (a rare card tying at a coincidental ceiling when `joint == marginal_j` exactly); it
  doesn't address the general "ratio ignores volume" issue lift and PMI both share.

The Cultivate row is the honest counterexample kept front-and-center rather than smoothed over:
t-score's top-4 for Cultivate (Champion of Lambholt, Heronblade Elite, Torens Fist of the
Angels, Kodama's Reach) are all popular, well-evidenced pairings — t-score isn't *wrong* — but
it demotes the one pairing that's actually thematically precise (two near-identical ramp
spells) below several that are just generically excellent, broadly-played cards with no special
connection to Cultivate. PMI's answer is arguably the *more correct* one for this specific card,
even though PMI is the noisier metric in general. One partial counter-counterexample: for
Moorland Rescuer, `Celebrate the Harvest` lands in *both* PMI's top-5 and t-score's top-6 off
the same 20-deck evidence base — the two metrics don't *always* diverge.

## Impediments
- **A pandas gotcha cost a silent, wrong-not-crashing bug in `my_kyler_deck.ipynb`**: a list of
  `(name_or_None, value_or_nan)` tuples built the `synergizes_with` column via plain Python
  `None`, but pandas silently converts `None` → float `NaN` on assignment into an object-dtype
  column. A downstream `if partner_name is None: return float("nan")` guard in the `pair_count`
  helper never matched, so instead of returning `NaN` for the 18 cards with no lift data, it
  fell through to a SQL join against a `NULL` partner id — which SQL correctly answers with 0
  rows, silently producing `pair_count = 0` (a real, plausible-looking, *wrong* number) instead
  of "not applicable." Fixed with `pd.isna()` in place of `is None`. Caught by inspecting the
  actual rendered table, not a test — worth remembering as a general pandas trap.
- **`precon_exploration.ipynb`'s own section 2/3 trust calculation had a real bug**, found
  while investigating a user's "something feels off" report about oddly-similar raw-vs-weighted
  box plots: a notebook cell called `deck_precon_trust(len(tracked & cardset), len(tracked))` —
  passing *overlap-card-count* and *precon-list-size* into a function whose real signature is
  `deck_precon_trust(diff, deck_total)` (physical-card difference from the precon, out of the
  deck's own total). The production code (`cooccurrence.py`'s `_precon_card_weight_overrides`)
  was already correct; only this notebook's independent re-derivation had the bug. For one real
  example (a Roaming Throne deck), the bug computed trust 0.83 where the correct formula gives
  ≈0.29 — a large, meaningful error, not a rounding difference. Fixed by threading `diff`/
  `deck_total` through from `best_matching_precon` instead of re-deriving a proxy.
- Writing the Cultivate/Kodama's Reach counterexample into the devlog required actually pulling
  real deck counts rather than trusting a first-draft guess — an early pass at this write-up
  claimed "1000+ shared decks" for the t-score picks from a vague impression; the real number
  (95-139, out of 1,230 global decks) was caught and corrected before it shipped.

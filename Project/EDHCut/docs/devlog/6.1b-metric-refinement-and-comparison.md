# Task 6.1b — Metric refinement, precon-weighting redesign, and cross-notebook comparison
Date: 2026-08-06/07 | Status: done | Ad hoc follow-on to 6.1, not a numbered plan task

Started from a notebook card-image lookup that surfaced a real card-identity bug, and grew into
a precon-weighting redesign, a fourth association metric (t-score), and comparison notebooks to
decide which metric to carry forward.

## Decisions
- **T-score added** (`(joint - expected) / sqrt(joint)`, no smoothing constant, no discount —
  `sqrt(joint)` damps low counts natively). It answers "is this pairing well-*evidenced*" rather
  than "how much more than chance", trading precision for robustness against coincidence.
  **The user's go-forward choice for association ranking.**
- **Precon weighting redesigned twice**, ending at per-card weight gated by per-deck trust:
  only cards that shipped with the deck's matched precon are down-weighted, scaled by how much
  that specific deck still overlaps the precon. Trust also gates `precon_retention.py`'s own
  aggregation, not just `cooccurrence.py`'s consumption of it — previously any precon-matched
  deck contributed a full 1.0 of evidence however unrelated it looked. Trust is defined purely
  as `(diff, deck_total)`: `diff ≤ 10` → 1.0, `diff ≥ deck_total - 20` → 0.0, linear between.
  `PRECON_CUT_RATE_FULL_WEIGHT` dropped 0.40 → 0.05 after eyeballing the real cut-rate spread.
- Comparison was done with re-executed real numbers in notebooks rather than argued in the
  abstract.

## Bugs
- **`card_names` alias collisions silently erased real cards.** The old alias loop treated a
  card's full name and each face name as equal last-write-wins entries, so a later card could
  steal an alias from an unrelated earlier one. Live: the `layout: "prepare"` card
  `Emeritus of Truce // Swords to Plowshares` had stolen the *only* row for "Swords to
  Plowshares", leaving the real instant with zero resolvable rows. Of 55 `prepare` cards, 19
  have a spell face matching a real standalone card and 8 were actually broken (Lightning Bolt,
  Demonic Tutor, Brainstorm, …) — the other 11 resolved correctly by bulk-file-order luck.
  Fixed in `build_name_aliases()`: full names are claimed in a first pass, face aliases only
  fill unclaimed keys. Downstream, 7 `edhrec_card_stats` rows across 4 slots held the wrong
  oracle_id; re-fetched. Found via a notebook image lookup, not a test.
- **pandas `None` → `NaN` coercion produced a wrong-not-crashing number.** An object column
  built with Python `None` came back as `NaN`, so an `is None` guard never matched and the code
  fell through to a SQL join on a `NULL` id — which returns 0 rows, yielding a plausible-looking
  `pair_count = 0` instead of "not applicable". Use `pd.isna()`.
- **A notebook re-derived `deck_precon_trust` with the wrong arguments**, passing overlap-count
  and precon-size into a `(diff, deck_total)` signature — trust 0.83 where the correct value is
  ≈0.29. Production code was already correct; only the notebook's independent re-derivation was
  wrong. Found from a user's "something feels off" about oddly-similar box plots.

## Outcome
Done, 185/185 tests. Lift and t-score agree on direction by construction (Spearman ρ = 0.959
over 61,030 kyler pairs; `lift>1` iff `t>0`) but differ by more than an order of magnitude in
magnitude near t≈0 — the small-sample noise made visible. Lift pairs obscure cards with obscure
cards: a card's popularity and its lift-argmax partner's correlate at ρ = **−0.816**. PMI does
*not* fix this; its 6.1 discount only addresses the exact-ceiling tie case.

**Honest counterexample, kept deliberately:** for `Cultivate`, t-score's top picks are all
popular well-evidenced cards, and it demotes `Kodama's Reach` — the one thematically precise
pairing — to #4. PMI's answer is arguably more correct for that card even though PMI is noisier
overall. So the metrics may need to coexist: t-score where volume-robustness matters, PMI where
a precise low-volume signal shouldn't get buried. That choice is still open going into 6.2/6.3.

Also added `--max-decks` to the Archidekt harvester (implemented and tested, run handed to the
user) — all numeric findings here are pinned to the 300-deck-per-slot corpus and need
re-verifying after any larger harvest.

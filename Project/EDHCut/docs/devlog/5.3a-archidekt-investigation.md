# Task 5.3-A — Archidekt investigation
Date: 2026-07-29 | Status: done

Go/no-go gate before writing the harvester: check Archidekt's terms, confirm the real shape of
the deck and search endpoints, and decide on a client library. Full technical detail lives in
`docs/archidekt_api.md`.

## Decisions
- **ToS conflict escalated, not resolved silently.** `robots.txt` was permissive but the ToS
  bans "automated... requests, or queries". Presented the options to the user rather than
  deciding; the user chose to proceed after a survey found Archidekt's co-founder stating on
  their own forum that the read API is intentionally open and that EDHREC uses the same public
  endpoints. Reasoning recorded in `docs/archidekt_api.md` §1 so it stays re-derivable.
- **`pyrchidekt` → `mtg_parser`** (user's call): actively maintained, works through our own
  session. But `parse_deck()` drops the commander and exposes no deck metadata, so the
  harvester fetches deck JSON directly and `mtg_parser` is reserved for task 7.1.
- Search goes through the public search page's embedded `__NEXT_DATA__` JSON — the documented
  `/api/decks/v3/` route is internal-only (its pagination response leaks a private
  `10.142.0.44` address) and has been broken for external callers for at least 6 months.
- Partner pairs are found with `commanderName=<primary>` + `cardName=<other partner>`, then
  confirmed client-side by the `"Commander"` category. Four guessed second-commander params
  (`commanderName2`, `partnerName`, `commanders`, `secondCommanderName`) were all silently
  ignored; `cardName=` narrows 1000+ candidates to 43, of which only ~12% are real pairs.

## Outcome
Done, go. Key simplification for 5.3-B: `oracleCard.uid` is Scryfall's `oracle_id` verbatim
(verified against our own `cards` table), so no fuzzy name resolution is needed for
Archidekt-sourced decks. Note for task 8.1: Archidekt asks for attribution on published
derived data.

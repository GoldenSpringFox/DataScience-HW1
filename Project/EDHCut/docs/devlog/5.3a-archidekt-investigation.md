# Task 5.3-A — Archidekt investigation
Date: 2026-07-29 | Status: done

## Goal & hypothesis
Before writing any harvester code, check whether Archidekt's `robots.txt`/ToS actually permit
what the plan assumed ("historically tolerated for respectful use"), and confirm the real
technical shape of the deck-by-id and deck-search endpoints plus what `pyrchidekt` (the
plan's original library pick) actually exposes. Plan §10 calls this "the go/no-go moment" —
treated it as one.

## Data
No bulk data pulled (this is an API/legal investigation task, not ingest). Touched: Archidekt
`robots.txt`, `/terms` ToS page, 3 of their own forum threads, one real deck fetched by ID
(`24392195`), one filtered search page (`commanderName=Krenko, Mob Boss`, ~5 pages / ~60
results per page inspected), and cross-referenced one card's identity against our own 30,574-
row `cards` table from task 5.2.

## Method & design decisions
- **ToS conflict, not silently resolved**: `robots.txt` was permissive, but the ToS text
  literally bans "automated... requests, or queries" — a direct conflict with the harvester.
  Rather than deciding this unilaterally, stopped and presented it to the user with four
  options (proceed on gray-area precedent / seek explicit permission / drop Archidekt as a
  source / pause with no code). **User chose to pause first**, then asked for a broader
  survey of alternatives (other tools, the EDHREC-Archidekt relationship, other decklist
  sites) before deciding.
- That survey turned up Archidekt's own co-founder's forum posts stating the API is
  intentionally open for reading, that EDHREC uses the exact same public endpoints with no
  special deal, and inviting third-party use with attribution. **User then explicitly chose
  to proceed with Archidekt** on that basis — full quote and reasoning in
  `docs/archidekt_api.md` §1, since this is a decision that should be re-derivable later, not
  just asserted.
- **Verified rather than assumed** every technical claim before writing it down: didn't trust
  old forum posts or the plan's original endpoint guesses at face value — re-tested the
  exact "confirmed working" URL from a 2020 forum reply and found it now broken (`404
  Client Unavailable`), matching a more recent (6-months-old) forum report of the same
  error. Traced *why* (the pagination response leaks an internal private IP,
  `10.142.0.44`, proving `/api/decks/v3/` is an internal-only route) rather than just
  noting it doesn't work.
- **Found the actual working search path empirically**: rather than keep guessing query
  param names against the broken direct API, fetched the real public search *page* HTML and
  found it embeds a `__NEXT_DATA__` JSON blob (Next.js SSR) containing the same search
  results — the same general technique the plan already planned to use for EDHREC
  (`pyedhrec`'s build-ID trick), just discovered independently for Archidekt. The correct
  query param name (`commanderName`, not the guessed `commanders`) was ultimately supplied
  by the user after my own guessing attempts and UI exploration didn't land on it.
- **`pyrchidekt` → `mtg_parser` swap**: user's call, informed by the alternatives survey
  (`mtg_parser` is actively maintained — released 4 days before this task ran — vs.
  `pyrchidekt`'s last commit being 2025-10; and it works against Archidekt with a plain
  `requests`-compatible session, no special auth). Tested it end-to-end against a real deck
  through our own `RateLimitedSession` before committing to it in the plan. Found empirically
  that its `parse_deck()` excludes the commander card from its output and exposes no deck
  metadata — decided the harvester should fetch deck JSON directly rather than depend on
  `mtg_parser` for it, reserving `mtg_parser` for task 7.1 instead (see
  `docs/archidekt_api.md` §3 for the reasoning).

## Evaluation & results
No pre-declared metric (this is a go/no-go + technical-discovery task, not an accuracy task).
Checks performed:
- `card.card.oracleCard.uid` on a real deck (`24392195`, commander Liesa, Shroud of Dusk) was
  queried directly against our own `cards.oracle_id` and returned an exact match —
  **confirmed** Archidekt reuses Scryfall's `oracle_id` verbatim, not an internal ID.
- `commanderName=Krenko, Mob Boss&deckFormat=3` search: all 5 inspected results were
  correctly on-theme (mono-red, goblin-tribal decks) — filter genuinely works, not a
  no-op.
- `GET /api/decks/{id}/` tested live via our own rate-limited/cached session (not just a
  browser) — confirms it's usable from our actual ingest code path, not just interactively.
- `mtg_parser.parse_deck()` tested against the same session: 71 card entries returned for a
  real Krenko deck, 0 tagged `"Commander"` — confirms the exclusion behavior empirically
  rather than inferring it from source reading alone.
- Partner-pair detection, resolved after the user pointed at a real example deck
  ([7019846](https://archidekt.com/decks/7019846/50_the_ever_faithful_is_finaly_at_peace)):
  both `Yoshimaru, Ever Faithful` and `Bruse Tarl, Boorish Herder` carry
  `categories: ["Commander"]` on that deck — category-based commander detection holds for
  partner pairs, not just single commanders. Also tested and rejected 4 guessed
  second-commander search params (`commanderName2`, `partnerName`, `commanders`,
  `secondCommanderName`) by comparing actual result-ID lists, not just the (unreliable,
  capped-at-1000) `count` field — all were silently ignored. And found a concrete
  false-positive case (deck `4443632`, Bruse Tarl present but tagged only `["Creature"]`)
  proving that card presence alone isn't sufficient evidence of a declared partnership.
- User then supplied the actual working refinement: `cardName=<other partner>` alongside
  `commanderName=<primary partner>` **does** filter server-side — not commander-specific
  (still just "card present somewhere"), but a real, working param unlike the 4 guessed
  ones. Measured its value precisely: `commanderName=Yoshimaru` alone → 1000+ (capped)
  candidates; adding `cardName=Bruse Tarl` → an exact **43**. Checked all 43 individually —
  only **5 (≈12%)** were actually `"Commander"`-tagged; the other 38 mostly maindeck Bruse
  Tarl for his lifegain trigger under a different (or no) partner. Net effect: ~23x fewer
  candidates to fetch for the client-side check, at the cost of an expected ~8x
  fetch-to-keep ratio once the check runs — a large, precisely-quantified efficiency win
  over the plain `commanderName`-only fallback.

## Interesting findings
- Archidekt's public bulk-data-style search API has quietly broken for external callers
  since at least 6 months ago and the plan's assumptions (and even a "known good" 2020
  forum example) no longer work — good example of why 5.3-A existed as a gate before 5.3-B
  rather than trusting old documentation.
- The `oracleCard.uid` = Scryfall `oracle_id` finding is a genuine simplification for 5.3-B:
  the plan's `card_names` fuzzy-resolution machinery (built in task 5.2 for exactly this kind
  of problem) turns out to be unnecessary for Archidekt-sourced decks specifically — it's
  still essential for task 7.1's free-text parser, just not here.

## Impediments
- Spent a long stretch trying to reverse-engineer the search query parameter names through
  browser UI exploration (clicking "Advanced options", reading the accessibility tree) with
  no success — the actual working param name (`commanderName`) was ultimately given by the
  user rather than discovered independently. In hindsight, going straight to inspecting the
  raw page HTML/`__NEXT_DATA__` payload (which is what eventually worked) would have been
  faster than UI archaeology from the start.
- The generic ToS boilerplate vs. the founder's specific forum statement is a real, slightly
  uncomfortable tension — a boilerplate legal document nominally overrides an informal forum
  post, but a specific on-the-record statement from the actual site owner is also
  meaningfully more informative about their actual intent than a copy-pasted template. Made
  sure this was the user's call, not something resolved by assumption, and documented the
  full reasoning in `docs/archidekt_api.md` so it can be revisited if circumstances change
  (e.g. if Archidekt's stance is ever restated less permissively).

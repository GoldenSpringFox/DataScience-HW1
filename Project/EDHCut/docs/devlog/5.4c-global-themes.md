# Task 5.4-C — Global EDHREC tag popularity ranking (themes + typal)
Date: 2026-07-31 | Status: done

Per-commander theme counts can't serve as a label vocabulary for task 6.6's clustering, which
needs a fixed globally-comparable list. Harvested EDHREC's site-wide tag browser — **270
themes + 131 typal tags = 401 rows** — into `edhrec_themes`.

## Decisions
- **Renamed the old table rather than dropping it**: 5.4-B's per-commander table became
  `edhrec_themes_per_commander` (user's naming request) via a migration that runs before
  `SCHEMA`, so the 285 already-harvested rows survive. A plain `CREATE TABLE IF NOT EXISTS`
  would have no-opped against the old shape.
- **Composite `(kind, theme)` primary key**, even though themes and typal have zero name
  overlap today — the widening cost nothing, and "true for all data seen so far" is not a
  guarantee (same lesson as 5.2's paper filter and 5.3-B's board rule). SQLite can't alter a
  PK in place, so the migration drops the old global table; safe, since it's wholly re-fetchable.
- **Two tables, not a `scope` column**: different primary keys and semantics, and `num_decks`
  isn't comparable across them.
- The global table refreshes wholesale on every run, unscoped by `--slot` — it isn't tied to
  any commander, and both fetches are cached.

## Bugs
- None. One trap worth flagging: on tag pages the `id`/`sanitized`/`slug` fields describe a
  *representative card thumbnail*, not the tag — the same field names `extract_card_stats`
  reads with a completely different meaning. Don't merge those two functions.

## Outcome
Done, 99/99 tests. Migration verified against the real DB, not just a fixture: the 285
per-commander rows and 1,177 card-stat rows came through untouched. Task 6.6 can now use
`edhrec_themes` as its label vocabulary.

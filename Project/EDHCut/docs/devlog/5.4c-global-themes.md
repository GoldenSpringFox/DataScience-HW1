# Task 5.4-C — Global EDHREC tag popularity ranking (themes + typal)
Date: 2026-07-31 | Status: done

## Goal & hypothesis
User feedback on 5.4-B: `edhrec_themes_per_commander` (then still named `edhrec_themes`) only
gives per-commander-slot tag counts — useful for describing one commander's own build space,
but not a usable input for task 6.6's planned k-means clustering, which needs a single, fixed,
globally-comparable theme vocabulary to label clusters against. EDHREC publishes exactly that
at `edhrec.com/tags/themes` — a site-wide, popularity-ranked list of every theme tag that
exists anywhere on EDHREC. Goal: harvest it into a new table, and free up the `edhrec_themes`
name for it (renaming the old per-commander table out of the way) per the user's explicit
naming request.

Immediate same-session follow-up: EDHREC actually splits its tag browser into two categories —
`/tags/themes` (mechanical/archetype tags, e.g. "Aristocrats") and `/tags/typal` (tribal/
creature-type tags, e.g. "Goblins") — user asked for typal added into the same table so the
clustering vocabulary wouldn't be missing a whole category.

## Data
Investigated `edhrec.com/tags/themes` live: same Next.js `__NEXT_DATA__`/build-ID/
`/_next/data/<build_id>/...` mechanism as commander pages (`docs/edhrec_api.md`), but the
payload shape differs slightly — `pageProps.data` has no `panels` key (only `container`), and
the theme list itself is a single cardlist tagged `"tagsbypopularitysort"` inside
`container.json_dict.cardlists`, already sorted descending by `num_decks`. Confirmed live:
**270 themes**, range 196,845 decks ("Tokens") down to 1 deck ("Value Vintage"), no pagination
— the whole ranking is one response. `/tags/typal` turned out to be the identical mechanism and
shape: **131 typal tags**, 26,650 ("Dragons") down to 4 ("Nobles"). Checked for name overlap
between the two lists before designing the schema — zero, currently.

Each cardlist entry's `id`/`sanitized`/`slug` fields turned out to describe a *representative
card* EDHREC shows as that theme's thumbnail (e.g. "Skullclamp" for the "Tokens" theme) — not
the theme itself. Initially confusing since these are the same field names `extract_card_stats`
already reads for actual cards. The theme's own identity is `name` (display name, e.g.
"Tokens") and `url` (e.g. `"/tags/tokens"`), the latter parsed into a stable `slug` column.

## Method & design decisions
- **Schema change, migration, not a fresh table**: renamed the existing `edhrec_themes` (task
  5.4-B, per-commander, PK `(commander_key, theme)`) to `edhrec_themes_per_commander`, and
  gave the `edhrec_themes` name to the new global table — exactly as the user asked. Since the
  local DB already had 285 real harvested rows in the old-shaped table, a silent `CREATE TABLE
  IF NOT EXISTS` would either no-op against the old shape or discard that data. Added
  `db._migrate_legacy_edhrec_themes_table()`, which detects the old shape by its
  `commander_key` column and renames it *before* `SCHEMA` runs — verified live: all 285
  per-commander rows survived untouched.
- **Composite `(kind, theme)` primary key, not `theme` alone**: for the typal add-on, even
  though themes/typal have zero name overlap today, nothing guarantees that stays true, so the
  key was widened defensively rather than waiting for a real collision. SQLite can't `ALTER` a
  primary key in place, so the same migration function grew a second case: detects the
  bare-`theme`-PK shape via a missing `kind` column and `DROP TABLE`s it (safe — this table is
  wholly derived/re-fetchable, unlike `edhrec_themes_per_commander`'s harvested-corpus data,
  which the first migration case still preserves via rename).
- **Two tables (global vs. per-commander), not one column added**: considered a `scope` column
  on a single table, but rejected it — genuinely different primary keys and semantics
  (`num_decks` isn't comparable across the two at all) would need nullable columns and manual
  scope-filtering everywhere it's queried.
- **Generalized fetch/extract functions, not per-page duplicates**: `/tags/themes` and
  `/tags/typal` are structurally identical (and neither has a `panels` key, so neither can
  reuse `fetch_commander_data`'s validation as-is) — `fetch_global_tag_page`/
  `extract_global_tags` take a `kind` parameter (`"theme"`/`"typal"`) instead of two near-copies
  of the same function.
- **Global tag table refreshes every run, unscoped by `--slot`**: since it's two cheap fetches
  (14-day cache, same as everything else EDHREC) and not tied to any particular commander slot,
  `run()` fetches both kinds once up front regardless of which slots are being harvested, and
  writes them together in one wholesale replace so the table's never left holding only one kind
  mid-refresh.
- **No new ToS investigation for either page** — same site, same page-family mechanism already
  covered by 5.4-A's decision (confirmed `robots.txt` doesn't block either route); each is one
  additional cached one-time fetch, not a new category of request volume or risk.

## Evaluation & results
- Unit tests: covering both `/tags/themes` and `/tags/typal` (fetch/extract/harvest, including
  the combined-write path and the `kind` column) plus the existing per-commander tests updated
  for the renamed table — **99/99 passing**.
- Live run: **270 theme rows + 131 typal rows = 401 total** in `edhrec_themes`, matching the
  live pages' own counts exactly (spot-checked top entries of both against the live site).
- Migration verified against the real local DB, not just a fresh `tmp_path` fixture: 285
  pre-existing per-commander rows landed intact in `edhrec_themes_per_commander`;
  `edhrec_card_stats` (1,177 rows) was untouched by either schema-migration pass.

## Interesting findings
- EDHREC's own site organizes the themes *page* hierarchically by color identity for display,
  but the underlying JSON is flat — a single popularity-sorted list, no color grouping in the
  data itself. Saved having to reconstruct or flatten a nested structure.
- The `id`/`sanitized`/`slug` "representative card" fields on these pages' cardviews are a trap
  if read the same way as `extract_card_stats` reads them for actual card cardlists — same
  field names, different meaning. Worth flagging for anyone touching `extract_global_tags`
  later: don't refactor it to share code with `extract_card_stats` without re-checking this.
- The "zero overlap between themes and typal" fact, while true today, was worth designing
  around rather than trusting outright — same general lesson as 5.2's paper-filter bug and
  5.3-B's board-membership rule: a heuristic that holds for all currently-known data isn't a
  guarantee, and the cost of the composite key was near-zero versus retrofitting it later.

## Impediments
None of substance — both pages turned out to use the same underlying mechanism already
understood from 5.4-A/5.4-B, so this was mostly straightforward extension work once the
schema-migration approach was decided.

## Notes for future work
- `edhrec_themes.slug` is stored but not yet consumed anywhere — kept for a possible future
  per-tag EDHREC page fetch (e.g. "get the top cards for the Aristocrats theme globally"), not
  needed by anything currently planned.
- Task 6.6 (archetype/theme clustering) can now use `edhrec_themes` as its fixed label
  vocabulary — cross-reference cluster centroids against this table by name (exact match) or
  fuzzy match if a cluster's dominant theme doesn't literally appear in this list.
- If EDHREC ever adds a third tag-browser category beyond themes/typal, the `kind` column and
  `GLOBAL_TAG_URL_TEMPLATES` dict in `edhcut/ingest/edhrec.py` are the two places to extend —
  the harvest/write logic already generalizes to any number of kinds without further change.

## Goal & hypothesis

Detect card "synergy communities" — recognizable packages like "goblin payoffs" or "sac
outlets" — via graph community detection over the association data task 6.1 already built. The
plan's own success criterion is qualitative and set before looking at output: printed clusters
should read as real archetype packages when eyeballed, not need a human to squint or rationalize.

## Data

Card pool at the initial build: 4,798 cards (task 6.1's `MIN_DECK_COUNT=3` pool) over the
5-commander roster corpus, 3,921 decks. Global t-score matrix (`tscore_global.npz`) reused
directly from task 6.1, not recomputed.

## Method & design decisions

Three deliberate deviations from the plan's literal wording, each decided explicitly with the
user before implementation, not assumed:

1. **Global scope only, not per-slot.** `cluster_of()` needs to generalize to any deck,
   including a commander outside the 5-slot roster — per-slot clusters wouldn't exist for an
   unseen commander at all, and v1's own scope already rejects unsupported commanders entirely.
   Checked live before deciding: per-slot t-score matrices are mostly empty rows for the same
   thin-corpus reason task 6.6 already flags for archetypes (64–96% zero-degree cards depending
   on slot, worst at Orysa 95.9%), so the marginal value of per-slot clustering over a global
   fallback would have been weak even setting the generalization argument aside.
2. **t-score, not PMI**, per the deferred decision flagged in devlog `6.1b` — PMI ties rare
   coincidental pairs at a ceiling value, exactly the kind of noise a "recognizable package"
   check would surface as spurious tight clusters rather than real structure.
3. **Only the 5 basic land types (+ Wastes, + snow variants) excluded as graph nodes** — not all
   lands, and not decided up front. See Interesting Findings below for the two-round live
   investigation this took.

Implementation (`edhcut/analysis/communities.py`): weighted undirected graph, each card's
top-`K=15` strongest *positive* t-score edges kept, union-symmetrized (an edge survives if
either endpoint keeps it in its own top-K — deliberately not "mutual," so a rare synergy piece
whose #1 partner is a much more generic staple isn't dropped just because that staple doesn't
return the favor). Leiden community detection (`leidenalg`, `RBConfigurationVertexPartition`);
resolution swept over `[0.25, 0.5, 0.75, 1.0, 1.5, 2.0]` at a fixed seed (42); best resolution
picked by modularity; seed stability checked via Adjusted Rand Index across 5 additional seeds.

## Evaluation & results

First real build (5-commander roster corpus): **6–11 clusters** across the whole resolution
sweep, the biggest containing **1,600+ of 4,767 graphed cards** — nowhere near "recognizable
packages." Modularity was actually respectable (0.66–0.67), which is what made this a genuine
diagnostic puzzle rather than an obvious bug — the math looked healthy while the output didn't.

Root cause, found by directly measuring cluster/slot purity rather than trusting the modularity
score: each cluster is almost exactly one commander's own deck pool.

| cluster | dominant slot | purity |
|---|---|---|
| 0 | krenko | 80.9% |
| 1 | kyler | 66.9% |
| 2 | yoshimaru_bruse_tarl | 97.0% |
| 3 | yenna | 98.8% |
| 4 | orysa | 98.4% |

t-score's null model (`E = N·p_i·p_j`) draws its marginals from a corpus that is five
commanders' decks pooled, not a metagame sample — so any two cards from the same slot score
high purely for co-slot membership, independent of real synergy. Measured directly on real
pairs (`t_pool` = as implemented; `t_strat` = a within-slot-stratified alternative, prototyped
to confirm the diagnosis, not adopted for production — see Impediments):

| pair | O (shared decks) | t_pool | t_strat |
|---|---|---|---|
| Goblin Warchief + Skirk Prospector | 1,696 | 20.58 | 0.98 |
| Champion of Lambholt + Heronblade Elite | 986 | 22.09 | 1.93 |
| Sythis, Harvest's Hand + Setessan Champion | 256 | 14.64 | 0.95 |
| Sol Ring + Arcane Signet | 2,143 | 5.27 | 4.90 |

The top three lose ~95% of their score under stratification — real synergy is a small residual
sitting on top of a much bigger confound. Sol Ring + Arcane Signet (not slot-specific) barely
moves, which is the control case confirming the diagnosis rather than an artifact of the
stratification math itself.

## Interesting findings

- **Land handling took two rounds of live investigation, not a one-shot decision.** Round 1,
  before any real build: checked Skirk Prospector's actual t-score row. Command Tower scored
  strongly *negative* (correctly detected as anti-correlated with mono-red aggro, no domain rule
  needed) but Mountain sat inside the top-15 goblin-package neighbors, indistinguishable in
  score from genuine members — a mixed enough picture that "exclude all lands" would have been
  an unjustified blanket rule. Round 2, after the mega-cluster problem surfaced with lands
  included: checked graph degree directly. Plains/Forest/Mountain had degree 1,000+ against a
  median of 15 and a next-highest of 660 (Champion of Lambholt — itself a legitimately high-
  degree *package-internal* hub, not a bridge). Mountain's own top-15 t-score partners were
  literally the goblin package — real, non-noise correlation, just not synergy: most red decks
  run enough Mountains regardless of theme. Excluding only the 5 basic land types (not Command
  Tower, not a hypothetical utility land) is narrowly justified by a mechanical distinction (zero
  oracle text, fungible within a color) rather than a general "exclude popular cards" rule.
- **Excluding basics alone did not fix the mega-cluster** — it barely moved (1,657 → 1,624
  cards). The next-highest-degree cards afterward were a mix of genuine package anchors (Goblin
  Warchief, degree 584 — expected, fine) and cards that were still cross-cutting (Command Tower,
  degree 649). Pushing the resolution parameter to 5.0, well past what modularity would ever
  pick, only shrank the biggest cluster to ~350 cards while modularity fell from 0.67 to 0.44 —
  confirming this was never a resolution-tuning problem, which is what motivated actually
  measuring cluster/slot purity instead of continuing to tune parameters.

## Impediments

The core impediment was diagnostic, not a code defect: `build_and_save` ran cleanly, tests
passed, and the graph/Leiden mechanics all worked exactly as designed. The confound is a
property of the *data* (five concentrated commander slots) interacting correctly with a metric
(t-score) that was validated for a different purpose — ranking associations within one corpus,
task 6.1 — and never checked for this one (building a graph across a multi-commander corpus).
Same lesson task 6.1 already learned once with the PMI ceiling-tie bug: a plausible aggregate
metric (modularity, here) doesn't substitute for a qualitative check of the actual output.

Two remedies were seriously considered:

1. **Stratify the t-score null model by slot** (`E = Σ_s N_s·p_i^(s)·p_j^(s)`). Prototyped and
   validated — the top stratified pairs were exactly the packages this task wants (Dragon
   Fodder/Hordeling Outburst/Krenko's Command; Ashnod's Altar/Phyrexian Altar/Thornbite
   Staff/Umbral Mantle). But it has a real degeneracy: as a stratum's sample size shrinks toward
   1, the stratified expectation converges on the observation itself and the statistic goes to
   zero — it does not combine with a wide-but-shallow sample, which is exactly what actually
   fixing the confound requires.
2. **Broaden the corpus so no single commander dominates** (task 5.7 — the metagame sample
   harvest, decided as the primary fix, in progress as of this writing). With ~1,000 commanders,
   no stratum is large enough on its own to be a confound, and pooled marginals approximate
   genuine metagame frequencies — stratification becomes unnecessary for the global scope, kept
   only as a documented fallback for roster-scoped analyses where strata are large enough to
   estimate in the first place.

## Rebuild (2026-08-10)

Task 5.7's metagame harvest completed (996/996 eligible commanders, 13,207 decks total). Rebuilt
`cooccurrence.py` and `communities.py` against the combined corpus. Card pool grew from 4,798 to
**18,979 cards** at `MIN_DECK_COUNT=3`.

**The matrix-scale guardrail fired as designed** (`assert_dense_matrix_safe`, added as part of
task 5.7 §6): 18,979² × 8 bytes = 2.68 GiB, over the 2 GiB ceiling. But measuring what the real
build actually allocates — not the guardrail's `n²` worst case — showed the alarm was checking a
scenario the code never hits: 10,666,504 nonzero pairs at 5.9% density, PMI/t-score sparse
matrices ~63 MiB each in memory, ~40x under the naive dense estimate, because nothing in either
module performs a full-pool dense conversion (confirmed by the same code audit task 5.7 §6(a)
already did). Removed the two blanket `assert_dense_matrix_safe` calls from `build_and_save` in
both modules (kept the function and its one genuine call site, `plot_matrix_overview.py`'s
heatmap, which does call `.toarray()` on a bounded submatrix). `MIN_DECK_COUNT` stays at 3 — real
memory scales with nnz, not `n²`, so it stays in the tens-of-MB range even as the corpus grows
further, which matters for the eventual deployment goal.

**First rebuild still showed a real, smaller residual confound.** Re-measuring cluster/slot
purity (26 clusters this time, not 5) found the pooled-corpus fix worked broadly — most clusters
spread across 700-1,000+ distinct commanders at 1-20% purity — but 3 clusters were still
disproportionately traceable to Krenko/Kyler/Yenna specifically (57.8%/59.2%/42.7% purity in an
intermediate check). Root cause: broadening the corpus fixes the *pooled* confound (no single
commander is a large share of ~1,000), but does nothing about these 3 commanders still carrying
their full oversampled roster deck count (thousands vs. ~9 decks typical) — the harvest's own
"roster commanders are not re-harvested" decision (5.7 §Decisions, item 6) means their relative
oversampling didn't shrink at all.

**Fix**: `edhcut.analysis.deck_weights.compute_near_uniform_weights(conn)` — new,
`weight_s = median(decks_per_slot) / n_s` over every slot actually in `decks` (not restricted to
`meta_commanders`, so it also catches Yoshimaru+Bruse Tarl and Orysa, both oversampled relative
to a typical slot despite falling below the `meta_commanders` threshold). Flattens every
commander's *total* weighted contribution to the same value, independent of real-world
popularity. Mid-session correction worth recording: this was almost implemented as
`compute_deck_weights` (the existing `true_share/sample_share` formula) instead — wrong, that
formula restores a commander's *true* metagame share (still large for a genuinely popular
commander), which is what play-rate/staple analyses want, not what communities wants. Caught by
re-reading `deck_weights.py`'s own docstring before wiring anything in.

`build_cooccurrence` gained an optional `deck_slot_weights: dict[str, float] | None` parameter —
multiplies each deck's contribution (on top of the existing per-card precon-novelty weight), and
`total_weight` (the t-score null model's `N`) becomes the weighted sum rather than a plain deck
count, so the two stay consistent. Wired into `communities.py`'s `build_and_save` only, by
explicit decision with the user: `top_associated`/the PMI "cards similar to X" lookup keeps the
unweighted global scope, since the plan only ever decided "near-uniform" for community detection
specifically.

**Verified the fix actually landed, not just assumed**: a known Krenko-confounded pair (Goblin
Warchief + Skirk Prospector) dropped from t-score 35.2 (unweighted) to 6.2 (weighted), joint
weight from 1,728 to 39.4 equivalent decks. Re-measuring purity is only a fair check under the
*same* weighting the graph itself used now — the raw/unweighted purity check that caught the
original bug stops being a fair lens once one commander has ~200x a typical slot's deck count,
since it'll show that commander "dominating" by sheer raw volume regardless of whether the
clustering is actually confounded. Under weighted purity: the top 11 clusters (holding the large
majority of the 18,297 graphed cards) all measured under 2% single-commander purity across
800-1,000 distinct commanders each. Only small tail clusters (low hundreds of cards) show higher
purity — expected for genuinely niche packages with naturally few supporting commanders.

**Qualitative eyeball check (the plan's own success criterion) passed**: Skirk Prospector's
cluster reads as Rakdos aggro/goblins (Blood Crypt, Chaos Warp, Impact Tremors, Goblin Warchief,
Lightning Greaves …); Cultivate's cluster reads as Naya ramp/midrange (Stomping Ground, Avacyn's
Pilgrim, Beast Within, Heroic Intervention …). Recognizable archetype packages, not one
commander's decklist — resolution 0.75 chosen by modularity (21 clusters, 0.6748), seed stability
mean ARI 0.651.

`playrate.py` also rebuilt (unweighted, no design change) against the same corpus: 13,207 decks,
31,623 cards, all 32 colour identities now populated (was 7/32 pre-harvest — the plan's own
predicted "expected side effect" of the harvest, confirmed). Wiring `compute_deck_weights`'s
true-share weighting into play rate itself (5.7 §Decisions item 4's "weighted for
play-rate/staples") is a separate, not-yet-implemented follow-up.

7 new tests (`compute_near_uniform_weights`, `build_cooccurrence`'s `deck_slot_weights`
parameter), 315/318 passing overall (3 pre-existing skips unrelated to this work).

## NMF soft clustering (2026-08-11)

User separately asked for soft/overlapping cluster membership (a card like Ashnod's Altar
genuinely belongs to more than one package — sac outlet, combo piece, ramp), which the hard
Leiden partition above can't represent. New module: `edhcut/analysis/nmf_packages.py`.

**Different input, so the confound/land problems needed independent (re-)verification, not
inherited from the rebuild above.** NMF factorizes the raw deck×card presence matrix directly
(not a derived pairwise association matrix), so both of `communities.py`'s fixes needed their
own version:

- **Oversampling fix: deck subsampling, not weighting.** sklearn's `NMF` has no native
  per-sample weight, and scaling a binary presence row by `sqrt(weight)` would corrupt the 0/1
  semantics the factorization relies on. Instead, every commander slot is capped at 25 decks
  (`MAX_DECKS_PER_SLOT`, matching the harvest's own per-commander ceiling), subsampled once with
  a fixed seed (`_sample_deck_ids`) before any k-sweep or stability check runs — 9,411 of 13,207
  decks survive the cap. Real, expected consequence: 204 cards whose only qualifying (>=3-deck)
  appearances all sat inside an oversampled slot's now-discarded excess volume dropped out of
  the training matrix entirely (`n_cards_dropped_no_signal`).
- **Land handling: exclude *every* land, not just basics — found live, not assumed.** First real
  attempt mirrored `communities.py` (basics-only excluded) and produced topics that read as
  color-pair mana bases, not synergy packages: Cultivate split across 5 different topics, each
  one's top members almost entirely that color pair's own dual/shock/check lands, Cultivate
  itself buried at 11-26% share in each. Root cause is specific to NMF's raw-presence
  factorization: a nonbasic land is present in the large majority of *every* deck sharing its
  color pair regardless of theme, an extremely strong, easy-to-fit block of correlated presence
  for Frobenius-loss NMF to spend components on. `communities.py`'s pairwise t-score never hit
  this failure mode — a land's association with any *one* specific other card stays weak, so its
  edges don't concentrate on a single archetype — which is why excluding only basics was
  sufficient there but not here. Excluding every land (`card_index["is_land"]`) fixed it,
  re-verified live: Ashnod's Altar went from smeared across 5-color-pair land topics to landing
  cleanly (75.9-79%) in a genuine aristocrats/sac-outlet topic (Zulaport Cutthroat, Skullclamp,
  Blood Artist, Pitiless Plunderer, Viscera Seer, Deadly Dispute); Cultivate to a clean ramp
  topic containing Kodama's Reach, the project's own standing regression check.

**k selection**: sweep `K_GRID=[15,20,25,30,40]`, each k fit at a primary seed (relative
Frobenius reconstruction error) and 3 stability seeds (topic-matching stability — Hungarian-match
each run's topics against the primary run's by cosine similarity over card weights, mean matched
similarity is the score; the NMF analogue of the Leiden rebuild's seed-stability ARI). Chosen k
maximizes stability. Real sweep result:

| k | stability | reconstruction error |
|---|---|---|
| 15 | 0.924 | 0.933 |
| 20 | 0.882 | 0.926 |
| 25 | 0.935 | 0.919 |
| 30 | 0.912 | 0.913 |
| **40** | **0.939** | **0.903** |

k=40 won, but it was also the grid's ceiling — checked whether stability kept climbing past it
before trusting the pick: extended the sweep to k=50/60/80, all scored *lower* (0.839, 0.893,
0.907), confirming k=40 is a real local peak, not a grid-boundary artifact.

**Verified the chosen (k=40) build directly, not just the sweep metrics**: Ashnod's Altar lands
76% in the aristocrats topic (Zulaport Cutthroat, Skullclamp, Blood Artist, Pitiless Plunderer,
Viscera Seer, Deadly Dispute, Morbid Opportunist) — tighter and more specific than at a smaller
k, though this particular card ends up concentrated in one topic rather than split, at this
resolution. Skirk Prospector lands 97% in a genuinely tight goblin-tribal package (Goblin
Warchief, Goblin Matron, Goblin Chieftain, Krenko Tin Street Kingpin, Impact Tremors, Goblin
Bombardment). Checked whether the flagship example concentrating into one topic meant overlap
wasn't actually happening in general — it isn't a fluke: **86.2% of the 17,658-card pool (15,229
cards) has genuine multi-topic membership** (2-5 topics each, `MIN_MEMBERSHIP_SHARE=0.10`).

**Outputs**: `nmf_card_memberships.parquet` (long format — `oracle_id`, `topic_id`, `weight`,
`share`, one row per card per topic it meaningfully belongs to), `nmf_deck_proportions.parquet`
(training-subsample decks only), `nmf_components.npy` (the `H` factor) +
`nmf_pool_index.parquet` for projecting *any* deck (`topic_proportions_for_deck`, via
`sklearn.decomposition.non_negative_factorization` with `H` fixed) — generalizes the same way
`communities.cluster_of` generalizes to unseen commanders, which is what task 7.2 needs for
"dominant synergy clusters (% of deck per cluster)."

14 new tests, 329/332 passing overall (3 pre-existing skips unrelated to this work).

## Soft-only pivot & open findings (2026-08-12)

**Hard clustering (`communities.py`) dropped from active use, decided by the user** — NMF's
soft membership subsumes it (a hard label is just a card's `argmax` topic when one is needed),
and maintaining two separate confound-fixes/land-handling decisions for the same underlying
problem across both modules wasn't worth it once NMF was validated. Code is untouched and still
tested, just no longer built into the notebook or workflow — available to revive if hard
partitions turn out useful again.

`notebooks/archive/communities_exploration.ipynb` rebuilt soft-only: no embedded card images (Scryfall
search links instead, `edhcut.images.scryfall_search_url`, reworked to always use the compact
`s:<set> cn:<cn>` form — new `cards.set_code`/`cards.collector_number` columns, backfilled via a
normal Scryfall re-ingest); full per-topic member tables (470-2,254 rows/topic) replaced with a
quick all-topics list plus top-10/bottom-5-by-`edhrec_rank` truncation per topic.

**Two problems surfaced by live user review of the notebook, one fixed, one open:**

1. **Granularity: 40 topics vs. EDHREC's own ~400-tag theme/typal taxonomy** (`edhrec_themes` —
   270 "theme" + 131 "typal" rows, already imported from task 5.4). Confirmed real, not a
   display issue — real topic content matches EDHREC's *biggest* themes (Goblins, Aristocrats,
   +1/+1 Counters — e.g. topic 37: Impact Tremors, Goblin Bombardment, Skirk Prospector, Goblin
   Warchief, Goblin Matron, Goblin Chieftain) but has no room for narrower ones (e.g. Humans
   typal — Heronblade Elite and Katilda, Dawnhart Prime don't share a dominant topic, each
   distributed across broader themes instead). Root cause: corpus depth, not the algorithm —
   both Leiden's resolution sweep (pushing to resolution 5.0 only reached ~350-card clusters
   while modularity collapsed 0.67→0.44) and NMF's own k-sweep (stability actively *fell* past
   k=40: 0.839/0.893/0.907 at k=50/60/80, all below k=40's 0.939) independently topped out well
   short of 400-way granularity, and the harvest itself was designed for commander breadth
   (25 decks/slot cap), not per-archetype depth. **Not fixed** — live recommendation, not yet
   acted on: use `edhrec_themes`/`card_tags` as a supervision signal (validate/name existing
   topics against them, or move toward semi-supervised classification) rather than push k/
   resolution harder — NMF fit cost scales ~k^2.25 (measured: k=15→3.3s, k=50→32.7s,
   k=100→191.2s, k=200→733.2s single-fit), so a full stability-checked sweep from k=10 to 500
   would cost on the order of a week of compute, not attempted.
2. **Same-color legality bias — confirmed and fixed for co-occurrence/t-score, not yet for
   NMF.** Two unrelated same-color cards (e.g. Swords to Plowshares + Felidar Retreat, both
   popular unrelated white staples) co-occurred *above* chance purely because they share a
   color-identity-restricted pool, not because of synergy. **Fixed**:
   `edhcut.analysis.cooccurrence.compute_color_conditioned_tscore` — full formula, the
   self-validating colorless-cancellation property, and the 20-pair live validation are in
   `docs/devlog/6.1-cooccurrence.md`'s own addendum, not repeated here. **NMF's own version of
   this bias is separate and still open** — NMF factorizes raw deck×card presence with no null
   model to correct, so this fix doesn't transfer mechanically; several topics show 80-93%
   single-color purity in the current build (topic 6: 93.3% colorless; topic 28: 90.0% red),
   plausibly a mix of genuine color-locked archetypes (Goblins really is red) and the same
   color-legality artifact, not yet disentangled. Measuring per-topic color purity (top-30
   members by `edhrec_rank`) is the diagnostic that surfaced this — worth re-running as a
   standing check if the NMF build changes.

## Notes for future work

- `CPMVertexPartition` (vs. the currently-used `RBConfigurationVertexPartition`) is worth trying
  for the hard-partition Leiden clusters — CPM has no modularity resolution limit and a directly
  interpretable resolution parameter, better suited to finer-grained packages than the current
  21-26 clusters.
- `compute_deck_weights`'s true-share weighting is still not wired into `playrate.py` — a real
  gap against 5.7's own decision 4, left as a follow-up rather than done opportunistically during
  the corpus rebuild.
- No precon-novelty per-card weighting in the NMF input (unlike `cooccurrence.py`'s pair counts)
  — a documented simplification, not yet revisited.
- Re-check cluster/slot purity (under the *weighted* lens, not raw — see the Rebuild section
  above) as a standing regression guard any time the corpus or weighting scheme changes again.

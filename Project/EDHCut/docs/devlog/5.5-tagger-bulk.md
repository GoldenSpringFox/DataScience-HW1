# Task 5.5 — Scryfall Tagger bulk tags
Date: 2026-07-31 | Status: done

## Goal & hypothesis
Populate `card_tags` (source='tagger_bulk') from Scryfall's official `oracle_tags` bulk file —
functional/mechanical tags (e.g. "removal", "boardwipe") crowdsourced by the Tagger project,
including ancestor tags via the hierarchy (a card tagged "boardwipe-creatures" should also get
"removal"). No ToS gate needed — bulk files are explicitly provided for this per plan §5.

## Data
Downloaded `oracle_tags` live: **5.6 MB compressed** (much smaller than the plan's older 18 MB
estimate — Scryfall's own bulk sizes drift over time). **4,505 tag objects, 230,624 total
taggings.** Checked the live shape against the plan's summary and found two corrections:
- Tag objects use `label` (free text, e.g. "grave pact") for display and `slug` (hyphenated,
  e.g. "grave-pact") for the stable identifier — not `name` as the plan said.
- No literal `category` field exists. Every object in this file already has `type == "oracle"`
  (confirmed: 4,505/4,505) — the separate `art_tags` bulk file is where illustration tags
  live — so "keep only functional/oracle categories" was already true by construction; no
  filtering code needed for it.
- Each tag carries its own `parent_ids` directly, so ancestor-walking needs no `child_ids`
  inversion (simpler than the plan assumed).

## Method & design decisions
- **`ancestor_slugs()`**: iterative walk up `parent_ids` with a visited-set, since a tag can
  have more than one parent (verified: not strictly a tree, a real DAG) — guards against both
  a diamond re-visit and a malformed cycle.
- **FK-driven filtering, not a name-lookup**: `card_tags.oracle_id` has an enforced foreign
  key to `cards` (`PRAGMA foreign_keys = ON`), so any tagging whose `oracle_id` isn't in our
  own `cards` pool is skipped and counted as unresolved rather than attempted — expected at
  scale, since Tagger covers all of Magic's history and our `cards` table is filtered to
  commander-legal cards only (task 5.2).
- **Extracted `expand_taggings()`** as a pure function (registry + known-oracle-id-set in,
  rows/stats out, no I/O) so the actual risky logic — hierarchy expansion, FK filtering,
  cross-tag dedup — is unit-testable without mocking the gzip download. Matches
  `archidekt.py`'s `_compute_deck_cards` precedent rather than `scryfall.py`'s (which leaves
  its whole `run()` untested); `run()` here is a thin wrapper.
- **Whole-source replace, not per-row upsert**: `card_tags` is scoped by `(oracle_id, tag,
  source)`, and this source is one bulk file, not per-item — `_write_card_tags` deletes all
  `source='tagger_bulk'` rows and reinserts, same idea as `deck_cards`/`precon_cards`'s
  delete-then-insert convention, just scoped by source instead of a single parent id.
- Small supporting refactor in `scryfall.py`: generalized `get_bulk_data_info(session,
  bulk_type)` (was hardcoded to `oracle_cards`) and renamed `iter_bulk_cards` →
  `iter_bulk_lines` (it was already fully generic, just named for its one caller) so this
  module could reuse both instead of duplicating them.

## Evaluation & results
- Tests: `ancestor_slugs`/`expand_taggings` covered directly (chain, diamond, dangling parent,
  cycle-safety, FK-skip, cross-tag ancestor dedup) plus `card_tags`/`tag_aliases`
  replace-not-accumulate write tests — 111/111 passing package-wide.
- Live run: **376,800 `card_tags` rows written**, **31,423/31,622 cards (99.4%) have ≥1 tag**,
  25,729 taggings skipped as unresolved (expected — non-commander-legal cards), **813 tag
  aliases**.
- Top tags by card count: `triggered-ability` (14,905), `activated-ability` (9,485), `cycle`
  (7,970), `card-names` (7,536), `removal` (6,114) — plausible general-purpose tags dominating,
  as expected for a crowdsourced functional-tag corpus.

## Interesting findings
- The plan's original `oracle_tags` field-name summary (`name`, `category`, `child_ids`-based
  hierarchy) didn't match the live API shape in three separate small ways — worth a reminder
  that even "no scraping needed, official docs exist" sources drift from an earlier
  investigation pass; checked live before writing extraction code rather than trusting the
  plan text at face value.
- **Found via manual user spot-check, not the original build**: Scryfall's own site search
  (`otag:boardwipe`) found cards even though no tag is literally named "boardwipe" — it
  resolves against a tag's `aliases` array (canonical tag `sweeper` carries `aliases:
  ["wrath of god", "mass removal", "wipe", "boardwipe"]`, 739 taggings). The original ingest
  read `slug`/`label`/`parent_ids` but never `aliases`, so alias-based lookups silently didn't
  work. Added `tag_aliases` (`alias_normalized` → canonical `tag`, 813 rows) to close the gap
  — **kept as a separate table rather than inserted as duplicate `card_tags` rows**, an
  explicit user decision, so an alias doesn't get double-counted as a distinct tag in
  downstream co-occurrence/clustering (task 6.x) — "boardwipe" and "sweeper" are the same real
  tag, not two. Checked live for alias-alias and alias-slug collisions before picking a bare
  `alias_normalized` primary key: zero found (813/813 distinct).

## Impediments
None of substance. The alias gap wasn't caught by the original build or its tests — surfaced
only when the user manually spot-checked `boardwipe`/`female` queries against the live data,
a good reminder that "the tests pass" and "the feature does what a real user expects" aren't
the same claim for a crowdsourced tag corpus with non-obvious lookup semantics (aliases).

## Notes for future work
- `card_tags.tag` stores `slug`, not `label` — if a later task (frontend, textmine tags) needs
  the human-readable label, it isn't stored here; would need a small lookup table or re-parse
  if ever needed.
- Tag `weight` (`median`/`strong`/`very_strong` in the raw data) isn't stored — `card_tags` has
  no weight column in the current schema. Flag if a future task wants tag-strength signal.
- Gender/character-depiction tags (what the user was originally probing for with "female")
  live in the separate `art_tags` bulk file (illustration-level, keyed by `illustration_id`),
  explicitly out of scope for this task per the plan — not ingested.
- Any query joining through `card_tags` on `edhrec_rank` should account for `NULL` ranks
  sorting first under plain `ORDER BY edhrec_rank ASC` in SQLite (seen live: two cards with
  no `edhrec_rank` sorted ahead of ranked ones) — filter `WHERE edhrec_rank IS NOT NULL` or
  sort `NULLS LAST` if "top by popularity" is the actual intent.

# Task 5.6 — QA & coverage report
Date: 2026-07-31 | Status: done

## Goal & hypothesis
Cross-source sanity report over everything tasks 5.2-5.5 harvested: per-slot deck/card-pool
sizes, deck-size sanity, unresolved-name leaderboards per source, tag coverage, an EDHREC-vs-
Archidekt inclusion agreement spot-check, Kyler's precon-similarity distribution, Orysa's
corpus thinness, and a resolve-check of the user's real decklist fixtures — as both a markdown
report (`edhcut/ingest/qa_report.py`) and the course EDA notebook
(`notebooks/01_data_overview.ipynb`, same queries + plotly charts).

## Data
No new harvesting — pure analysis over the already-populated `data/edhcut.db` (1,230 decks,
31,622 cards, 376,800 card_tags rows, etc. from tasks 5.2-5.5) plus the already-downloaded raw
bulk files and the Archidekt harvest audit log. The EDHREC unresolved-name re-check is the only
part that touches a live session, and it's cache-only within the 14-day window (verified: zero
new requests on a re-run).

## Method & design decisions
- **Two of `card_tags`/Archidekt's/Tagger's "unresolved" data was never persisted anywhere
  queryable** — the Archidekt harvester writes unresolved names only into its text audit log
  (not a DB table), Tagger's raw taggings carry only `oracle_id` with no name at all, and
  `edhrec.SlotEdhrecStats` truncates to a 10-name sample. Rather than retrofitting three
  existing ingest modules' schemas for a one-off report, this re-derives all three from what's
  already on disk: Archidekt's from the audit log text, EDHREC's by replaying
  `harvest_slot`'s fetch/extract/resolve steps against the cached session (no new requests),
  Tagger's by cross-referencing unresolved `oracle_id`s against the full unfiltered
  `oracle_cards.jsonl.gz` for a display name.
- **Deck-size sanity check needed a real fix, not just a query**: the naive version (stored
  `deck_cards` sum vs. flat 99/98) flagged **23 false positives** — `deck_cards` deliberately
  excludes unresolved (e.g. now-banned) cards, so a deck legitimately containing one is shorter
  than 99/98 in storage even though the harvester validated its *true* size before keeping it.
  Fixed by reconciling against each deck's own unresolved-card count from the audit log
  (`_kept_deck_unresolved_counts`, matching only genuinely-kept log lines, not
  rejected-candidate ones for the same URL). That brought it down to 2 real remaining
  mismatches — investigated rather than dismissed: both decks turned out to have **more than 2**
  Archidekt `"Commander"`-tagged cards (a Partner-with/Background chain — e.g. deck 4456720
  tags Bruse Tarl, Kediss, Rograkh, *and* Ardenn all as `"Commander"`), which
  `decks.partner_oracle_id` can only represent up to 2 of. Verified live against the cached
  deck JSON using the harvester's own `commander_cards()`/`_compute_deck_cards()` that their
  stored row counts are internally correct relative to their *real* commander count — the
  check is correctly flagging a schema edge case, not corrupt data.
- **Comma-in-card-name bug in the audit log parser**: the log joins multiple unresolved names
  with `", "`, which is indistinguishable from a comma *inside* one card's own name (e.g.
  "Orcrist, Goblin-cleaver", "Thorin, Mountain-king", "Sting, Bilbo's Sword" — all real LOTR
  cards). A naive split fragmented these into fake half-names. Fixed with
  `_resplit_comma_joined_names`: greedily re-merges adjacent fragments whenever the merge
  matches a real name in the full (unfiltered) Scryfall name set — verified against the three
  known real fragmented cases plus that ordinary non-comma names pass through unchanged.
- **Minimal fixture-decklist parser, not task 7.1's general one**: `data/fixtures/my_decks/`
  documents its own small format (quantity-prefixed lines, `Commander:`/`*CMDR*` markers,
  comments/blanks ignored) — `parse_fixture_decklist` targets exactly that, not the general
  multi-site parser task 7.1 will build.
- **Notebook reuses `qa_report.py`'s functions directly** rather than re-deriving the same
  queries a second time in notebook-only code — every chart's underlying numbers are
  identical to the markdown report's, by construction, not by keeping two implementations in
  sync manually.
- Added `plotly`/`jupyter`/`nbformat` as a `notebooks` extras group in `pyproject.toml`
  (`pip install -e ./Project/EDHCut[notebooks]`) rather than core dependencies — not needed to
  run the ingest pipeline or tests.

## Interesting findings
- The QA report caught two real, previously-invisible bugs in its own supporting code before
  it caught anything about the underlying harvested data — the deck-size false-positive rate
  (23 → 0 after the fix) and the comma-fragmentation bug are both artifacts of how earlier
  tasks' logging happened to be formatted, not data quality problems with what was harvested.
  Good validation that this task's actual job (surfacing exactly this class of issue) works.
- Yoshimaru+Bruse Tarl's low EDHREC/Archidekt agreement (2/10) is a real, expected consequence
  of task 5.3-B's partner-fallback design (documented there) showing up correctly in a
  cross-source check built independently of that decision — the two tasks weren't cross-
  checked against each other until now, and it lines up.

## Impediments
- A subtle Jupyter/contextlib bug: `connect(db_path).__enter__()` without keeping a reference
  to the context-manager object itself let it get garbage-collected mid-notebook (Python
  running the generator's own `finally: conn.close()` on GC), closing the DB connection before
  later cells could use it. Fixed by holding onto the context-manager object
  (`_db_ctx = connect(...); conn = _db_ctx.__enter__()`) for the notebook's lifetime and
  calling `_db_ctx.__exit__(...)` explicitly in the final cell.
- `pandas.DataFrame({...})` from two lists of possibly-different length (EDHREC/Archidekt
  top-10s aren't always both length 10 for thin slots) raises rather than padding — needed an
  explicit pad-to-10 helper in the notebook's side-by-side comparison cell.

## Notes for future work
- `edhrec_analyzed_deck_count` (used for Orysa thinness and the cross-slot comparison chart)
  is derived (`num_decks / inclusion_rate`), not a value EDHREC exposes directly per slot —
  fine for this report, but if a future task needs it precisely, consider storing
  `container.json_dict.card.num_decks` directly in `edhrec_card_stats` or a new column instead
  of re-deriving it.
- If a future session wants the notebook's plotly figures to render reliably in a bare static
  viewer (e.g. GitHub's preview, not just Jupyter/VS Code), consider setting an explicit
  `kaleido`-based static-image fallback — not done here since the primary viewing path
  (Jupyter/VS Code, or `nbconvert --to html`) already renders the current output correctly.

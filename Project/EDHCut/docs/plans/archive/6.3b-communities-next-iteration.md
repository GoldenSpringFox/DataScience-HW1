## Baseline (measured 2026-08-12, saved k=40 NMF build)

**Color bias is real and large.** Per-topic color purity = share of the topic's top-30 members by
weight carrying the topic's modal color identity:

| statistic | value |
|---|---|
| median purity across the 40 topics | **66.7%** |
| topics ≥70% / ≥80% / ≥90% purity | **19 / 15 / 8** of 40 |
| topic 6 (colorless) / topic 24 (mono-G) | **100% / 100%** |
| random null: 30 pool cards, 2,000 draws | median **23.3%**, p95 30.0%, max 46.7% |

Two topics are *perfectly* single-identity and the median topic is ~3× the null. Some of this is
genuine (Goblins really is red), but it is far too much to be all genuine.

**Granularity: the problem is bundling, not absence.** Using `card_tags` (source `tagger_bulk`)
restricted to the NMF pool with 20–3,000 cards per tag (953-tag vocabulary):

| statistic | value |
|---|---|
| tags enriched (lift ≥3, hypergeom p<1e-6, ≥5 cards) in ≥1 topic | **587 / 953** |
| all 39 `typal-*` tags in vocabulary, enriched somewhere | **39 / 39** |
| median distinct tags enriched **per topic** | **22** (min 2, max 46) |
| tags *resolved* — `min(share of topic, recall of tag) ≥ 10%` | **74 / 953** |
| tags resolved at ≥20% / ≥30% | **19 / 5** |

This reframes the granularity question usefully: the 40 topics already *touch* almost every theme
(587/953 enriched), but each topic is a **bundle of ~22 themes**, so almost no theme gets a topic
of its own. The best-resolved tag in the whole build is `burn` at 38.6% of topic 28. That is the
number to move — **not** "enrichment coverage", which is already near-saturated and would look
like success without being it.

## Q1 — Can NMF use the color-identity fix?

**Answer: not by patching NMF's input; yes by changing what gets factorized. Recommended: switch
the factorization input to the color-conditioned t-score matrix and use symmetric NMF.**

Why the current setup can't take the fix. `compute_color_conditioned_tscore` works by correcting a
**null model** (`expected' = N_ij · p_i · p_j`, where `N_i` counts only decks legally able to run
card *i*). NMF has no null model: it factorizes raw deck×card presence `X ≈ W H` under a Frobenius
loss, and colour-identity legality is *structural* in `X` — a mono-green card has literal zero
support outside green-legal decks. That block structure is the strongest low-rank signal in the
matrix, so components spend themselves on it. Non-negativity also forbids the obvious fix
(subtracting an expectation makes entries negative).

Two patches were considered and rejected:

- **Per-column/per-block rescaling of `X`.** Rejected on mathematics, not taste: scaling a column
  cannot change *where* that column has support. A green card still has zeros on every non-green
  deck at any scale, so the block structure survives untouched.
- **Fixed "color background" components** — append `k_bg` components whose `H` rows are frozen to
  each color identity's generic play-rate profile, so free topics fit only the residual. This is
  sound in principle but `sklearn` cannot freeze *part* of `H` (`update_H=False` freezes all of
  it), so it needs a custom multiplicative-update loop anyway — and if we're writing a custom loop,
  the option below is both simpler and reuses an already-validated correction. Also runs against
  the project's standing preference for not bolting a capability onto a method that lacks it.

**The recommended route.** The color fix already exists and is validated — it lives in the
*metric* (`compute_color_conditioned_tscore`, 20-pair live validation in
`docs/devlog/6.1-cooccurrence.md`), not in the clustering. So consume the metric instead of
re-deriving the correction:

```
S = max(t_color_global_weighted, 0)      # card × card, symmetric, non-negative
S ≈ H Hᵀ,  H ≥ 0,  H is (n_cards × k)    # symmetric NMF
```

Each column of `H` is a package; each **row of `H` is a card's soft membership vector** — the same
object `nmf_packages.py`'s `H` gave us, so the whole downstream API (`card_topics`,
`topic_members`, membership shares) survives unchanged. SymNMF is the standard soft/overlapping
relaxation of spectral graph clustering, so this is a named method, not an improvisation.

What this costs and buys:

- **Buys**: the color correction, exactly, with no new statistics invented; the colorless-
  cancellation self-check property carries over untouched; and (see Q2) it makes high `k`
  affordable for the first time.
- **Costs**: no `W` (deck→topic) factor. Recover it by projection — a deck's topic proportions =
  row-normalized `Σ_{c ∈ deck} H[c, :]`. Document this as a change in definition, not a drop-in.
- **Costs**: the land-exclusion decision reverts. All-lands exclusion was specific to raw-presence
  NMF (`nmf_packages.py`'s module docstring explains why); t-score does not have that failure mode,
  so this build should use `communities.basic_land_mask` (basics only) and **re-verify** the
  Cultivate/mana-base regression check rather than assume it.

## Q2 — More communities, and formalizing supervision

Three layers. Do them in this order; each one is the acceptance test for the next.

### Layer 1 — make "granular enough" a number

Already prototyped in the Baseline section above; Step 1 turns it into project code. For every
(topic, tag) pair compute a hypergeometric enrichment (Benjamini–Hochberg FDR across the full grid)
and report two different things, because they behave completely differently:

- **coverage / recall** — a theme is *covered* if any topic is significantly enriched for it.
  Already 587/953 at k=40. Near-saturated; report it, don't optimize it.
- **resolution** — a theme is *resolved* if some topic has `min(share_of_topic, recall_of_tag) ≥ τ`,
  i.e. the theme both dominates a meaningful fraction of that topic and is mostly captured by it.
  **74/953 at τ=0.10.** This is the objective function for the whole granularity effort.

Also report **themes-per-topic** (median 22 at k=40) — the direct measure of bundling.

Label sources, both already in the local DB, no scraping required:

- `card_tags` (`tagger_bulk`, 4,183 tags, 376,800 rows) — per-card multi-label, the primary signal.
- `edhrec_themes` (401 rows, 270 `theme` + 131 `typal`) — the *target vocabulary*, not per-card
  labels. Map theme → tag by: exact slug match (**42 of 401 hit exactly**, verified), plus the
  rule `typal` kind → `typal-<singularized name>` (210 `typal-*` tags exist, so typal coverage is
  near-complete), plus a small hand-written alias dict for the rest. Expect ~150–250 of 401 themes
  to get card-level labels this way; that is enough to steer on.
- *Optional, user-run, not in scope here*: harvesting the 401 EDHREC `/themes/<slug>` pages would
  give true card→theme labels for all 401. ~401 requests. Per standing preference, hand over the
  command rather than running it.

### Layer 2 — hierarchical decomposition (the cheap route to 200–400 packages)

Do **not** attack granularity with a wider flat `k` sweep. Instead recursively split:

1. fit SymNMF at a small top-level `k` (≈10–12) over the full card universe;
2. for each topic, take its member cards (`share ≥ τ_member`), induce `S` on just those rows/cols,
   refit SymNMF with small `k` (≈4–8);
3. recurse; stop a node when it has `< MIN_NODE_CARDS` (≈60) cards, or its children fail the
   seed-stability check, or splitting doesn't improve Layer 1's resolution metric.

This reaches ~200–400 leaves for a small fraction of the cost of one flat high-`k` fit (cost is
superlinear in `k`, so many small problems ≪ one big one), and it produces a **tree**, which is
also the deliverable Q3 is really asking for. Expose `cut_at(n_leaves)` and choose the cut by the
Layer 1 resolution curve, not by eyeball.

### Layer 3 — supervision, three distinct meanings

Name which one is wanted, because they're different deliverables:

- **3a. Post-hoc labelling (do this — it *is* Layer 1).** Enrichment gives every topic a name and a
  q-value ("topic 37 = Goblins, lift 19.9×, 81 cards"). Cheap, zero modelling risk, immediately
  usable in the final report, and it's the evaluation harness for 3b/3c.

- **3b. Anchored (semi-supervised) SymNMF — recommended.** This is the clean formalization of
  "supervised clustering based on these themes", and it is *one extra term*. Build a seed matrix
  `A` (n_cards × k), where a seeded column holds the (scaled) indicator vector of a theme's tagged
  cards and unseeded columns are zero. Minimize

  ```
  J = ‖S − H Hᵀ‖²_F  +  λ ‖(H − A) restricted to seeded columns‖²_F
  ```

  which changes the multiplicative update to (derivation: split ∂J/∂H into positive/negative parts)

  ```
  H ← H ⊙ [ (1−β) + β · (2·S H + λA) / (2·H (HᵀH) + λH + ε) ]        β = 0.5
  ```

  `λ = 0` is exactly unsupervised SymNMF; `λ → ∞` pins topics to the themes; anything in between is
  "start from human concepts, let the data refine them and discover the rest". **λ is the knob that
  makes this a spectrum rather than a binary choice**, and it is tuned against Layer 1's resolution
  metric on held-out themes (seed half the labelled themes, score recovery of the other half).

- **3c. Fully supervised multi-label theme classification — separate task, not this one.** Features
  = existing `embeddings.parquet` (w2v + TF-IDF/SVD) + color identity + tag/role features; labels =
  theme membership; one-vs-rest logistic regression → `P(theme | card)` for all 401 themes and
  every card, including cards with almost no deck data (the Orysa cold-start case the plan cares
  about). Genuinely attractive, but it stops being community *detection* — it's theme prediction,
  and it overlaps tasks 6.4/6.6. Keep the unsupervised chapter unsupervised; propose 3c as its own
  task if wanted.

## Q3 — Is Girvan–Newman relevant?

**Short answer: not as the algorithm, but the thing you want from it is worth building — from
cheaper methods — and one small GN figure is worth doing for the report.**

1. **Runtime rules it out, decisively.** Current graph: **n = 18,297 nodes, m = 221,507 edges**
   (`communities_manifest.json`). One edge-betweenness pass is O(nm) ≈ 4.1×10⁹ operations, and GN
   recomputes it after every edge removal — up to `m` removals → ~10¹⁵ operations. igraph's
   `community_edge_betweenness` exists and will not finish. Not a tuning problem.
2. **It's also the wrong output shape now.** GN yields a hard, nested partition. Ashnod's Altar
   belonging to both a sac-outlet and a reanimator package — the reason the project moved to soft
   membership at all — cannot be represented in a GN dendrogram.
3. **But the deliverable you described is real and obtainable.** "A dendrogram you can cut manually,
   plus modularity vs. number of clusters" is available from `igraph.Graph.community_fastgreedy()`
   (CNM, O(n log²n)), which returns a `VertexDendrogram`; `.as_clustering(n)` cuts at any level, so
   modularity-vs-n is a one-line loop. `community_walktrap()` is the same shape. Both are already
   dependencies. For the *soft* model, Layer 2's tree is the same control, plotted against the
   theme-resolution metric instead of modularity.
4. **Where GN genuinely earns a place: one figure.** Take a single topic's induced subgraph
   (~300–600 cards, ~3–6k edges), run *true* GN on it, and show the dendrogram of one package
   splitting into sub-packages. That's seconds of compute, directly demonstrates the algorithm from
   class on our own data, and the accompanying "here's why we can't run it globally" paragraph is
   itself good report material.
5. **A real insight that came out of asking this.** Modularity has a known resolution limit
   (Fortunato & Barthélemy 2007): communities with fewer than ~√(2m) internal edges tend to get
   merged. Here √(2·221,507) ≈ **666 edges**, and with mean degree 2m/n ≈ 24 that's roughly a
   50–100-card floor on detectable packages. So the devlog's conclusion that "both methods
   independently topped out near 40, therefore it's a corpus-depth limit" is only **half** right for
   the Leiden side — part of that ceiling is the objective function, not the data. `CPMVertexPartition`
   has no resolution limit and is the correct hard-clustering comparison (already flagged in the
   devlog's "Notes for future work").

## Implementation steps

### Step 0 — Fix weighted-vs-raw units in the color-conditioned null model *(blocking, small)*

**Bug, found while planning, not yet verified live.** `compute_color_conditioned_tscore` computes
`p_i = weighted_marginal_i / N_i`, but `N_i` comes from `eligible_deck_count`, which sums **raw**
deck counts from `build_color_identity_deck_counts`. That's fine today (the saved `tscore_color_*`
matrices are unweighted), but Step 2 needs it under `compute_near_uniform_weights`, where
`total_weight` ≈ 9,000 vs. 13,207 raw decks. Under a global scale factor α, `joint` scales by α but
`expected' = N_ij·p_i·p_j` scales by α², so the correction is systematically mis-scaled (α ≈ 0.68 →
expectation too small → under-correction).

- Add `deck_slot_weights: dict[str, float] | None = None` to `build_color_identity_deck_counts`;
  when given, sum each deck's weight instead of counting decks (keep the column name `deck_count`,
  but it becomes a weighted count — rename to `deck_weight` and update `eligible_deck_count` if
  that reads more honestly).
- Test: with `deck_slot_weights=None` the output is byte-identical to today's. With uniform weights
  `w=1.0` for every slot, identical again. With near-uniform weights, `total ≈ total_weight` of the
  matching `build_cooccurrence` result.
- Verify the fix moves the numbers: re-score 3–4 of the pairs from the 6.1 validation set under
  weighting, both before and after, and record both.

### Step 1 — `edhcut/analysis/theme_labels.py`: the measuring stick

Build this **before** any new clustering, and run it against the existing `k=40` build so the
baseline in this document is reproduced by code rather than quoted.

- `build_theme_labels(conn) -> pd.DataFrame` — `oracle_id`, `label`, `source` (`tag` | `theme`),
  `edhrec_theme` (nullable). Tag vocabulary filtered to 20–3,000 cards within the analysis pool.
  Theme→tag mapping: exact slug match, then `typal` kind → `typal-<singular>`, then an explicit
  alias dict; log and report how many of the 401 themes got labels.
- `topic_theme_enrichment(memberships, labels, *, min_cards=5, min_lift=3.0, fdr=0.01)` →
  long-format `topic_id`, `label`, `n_in_topic`, `lift`, `p`, `q`, `share_of_topic`,
  `recall_of_label`, `resolution = min(share_of_topic, recall_of_label)`. Hypergeometric `sf`,
  Benjamini–Hochberg across the whole grid.
- `granularity_report(...)` → the three headline numbers: `n_labels_covered`,
  `n_labels_resolved(τ)` for τ ∈ {0.05, 0.10, 0.20, 0.30}, `median_labels_per_topic`.
- `color_purity(memberships, conn, *, top_n=30, n_null_draws=2000)` → per-topic modal-identity
  share plus the random-null distribution. Keep the definition **identical** to the baseline above
  (top-30 by weight, modal color-identity string, colorless as its own identity `"C"`) so numbers
  stay comparable across builds.
- CLI: `python -m edhcut.analysis.theme_labels report --build nmf` printing both tables.
- **Acceptance**: reproduces the Baseline section's numbers (74/953 resolved at τ=0.10; median
  color purity 66.7%; 19/15/8 topics at ≥70/80/90%). Any disagreement is a bug in one of the two —
  find out which before continuing.

### Step 2 — `edhcut/analysis/symnmf_packages.py`: color-corrected soft packages

- Input build: `compute_near_uniform_weights(conn)` → `build_cooccurrence(conn, card_index,
  slot_key=None, deck_slot_weights=w)` → `compute_color_conditioned_tscore(...)` with Step 0's
  weighted eligible counts → `S = max(t, 0)`. Exclude basic lands via `communities.basic_land_mask`
  (**not** all lands — see Q1), drop zero-degree rows.
- Sparsification: default to `communities.build_graph`'s top-K union rule (factor that logic out
  rather than duplicating it) at `TOP_K = 50`; keep unsparsified positive t-score as a documented
  ablation.
- Solver — **write the multiplicative-update loop, don't reach for `sklearn`**:
  ```
  G = H.T @ H                       # k×k
  num = S @ H                       # sparse × dense
  den = H @ G                       # n×k, NEVER form H @ H.T  (18,979² float64 = 2.7 GiB)
  H  *= (1 - β) + β * num / (den + ε)          # β = 0.5
  ```
  Init `H = 2·sqrt(S.mean()/k)·rand(n, k)` with a fixed seed. Track the residual **without
  densifying**: `‖S − HHᵀ‖² = ‖S‖² − 2·sum((S@H) * H) + ‖G‖²_F`. Stop on relative-residual change
  `< 1e-5` or `MAX_ITER`.
- Why this is the affordable path, and the number to check first: per iteration ≈ `2·nnz·k` +
  `2·n·k²` flops — at k=200 that's ~5 GFLOP of pure BLAS-3, estimated a few minutes for a full fit,
  versus 733 s for a single `sklearn` CD fit at k=200 on the (smaller) deck×card matrix. **This is
  an estimate, not a measurement — time one k=40 fit first and report it before committing to a
  wide sweep.**
- Same public API surface as `nmf_packages.py` (`load_card_memberships`, `topic_members`,
  `card_topics`, `topic_members`), plus `deck_proportions` redefined as row-normalized
  `Σ_{c ∈ deck} H[c, :]` — document the definition change in the module docstring.
- Sweep `k` and pick by stability (Hungarian-matched cosine over `H` columns across seeds, reusing
  `nmf_packages._match_topic_stability`), **with Step 1's resolution metric reported alongside** —
  if stability and resolution disagree about the best `k`, that disagreement is itself a finding and
  should be recorded, not silently resolved.
- **Pre-declared acceptance criteria** (all three, measured, in the devlog):
  1. **Color**: the purity distribution moves toward the null. Target: median across topics ≤45%
     (from 66.7%, null 23.3%) and **zero** topics at 100%. Genuinely color-locked archetypes
     (Goblins) are *expected* to stay pure — judge the distribution, not individual topics.
  2. **Regression**: Ashnod's Altar still has meaningful membership in both a sac-outlet/aristocrats
     topic and a graveyard/reanimator topic; Cultivate still sits with Kodama's Reach; no topic
     reads as a color-pair mana base.
  3. **Granularity**: at comparable `k`, resolved-label count is no worse than the k=40 baseline
     (74 at τ=0.10). Step 3 is what's expected to actually move this.

### Step 3 — Hierarchical decomposition + manual granularity control

- `build_hierarchy(S, *, top_k=10, child_k=6, min_node_cards=60, min_child_stability=0.7)` —
  recursive SymNMF per Layer 2, storing each node's card set, `H` column, parent, depth, and its own
  stability score. Persist as `symnmf_hierarchy.parquet` + a small JSON tree.
- `cut_at(tree, n_leaves)` → a membership table with the same schema as Step 2's, so every
  downstream consumer and every Step 1 metric works on a cut without modification.
- Produce the two curves that make granularity a decision instead of a feeling: **resolved-label
  count vs. n_leaves** and **median color purity vs. n_leaves**, sweeping the cut from ~20 to ~400.
  Pick the operating point where resolved-label count saturates.
- **Acceptance**: at some cut ≤400 leaves, resolved labels at τ=0.10 reach **≥250 / 953** (from 74)
  and median labels-per-topic drops from 22 to **≤6**. If the curve saturates well below that, say
  so plainly and stop — that's the honest corpus-depth answer, and Step 4 is the response.

### Step 4 — Anchored (semi-supervised) SymNMF *(conditional on Step 3's curve)*

Only if Step 3 saturates below its target. Adds the `λ‖H − A‖²` term from Layer 3b — a one-line
change to Step 2's update. Seed matrix from Step 1's labels; tune `λ` by seeding half the labelled
themes and scoring recovery of the held-out half. Report the λ-sweep as a curve from unsupervised
(λ=0) to pinned (λ large), and pick a point deliberately — the interesting claim for the report is
the *shape* of that curve, not the winning value.

### Step 5 — Notebook: `notebooks/communities_exploration.ipynb`

Extend, don't rewrite. New sections, in this order:

1. **Color bias, before/after** — purity distribution for the k=40 NMF build vs. the new SymNMF
   build vs. the random null, on shared axes.
2. **Theme enrichment table** — every topic with its top-3 enriched labels and lift, replacing the
   current informal "top-3 members by EDHREC rank" labels.
3. **Granularity curves** — Step 3's two curves, with the chosen cut marked.
4. **Girvan–Newman, on one package** — induce the subgraph of one topic's members, run

5. **`community_fastgreedy` global dendrogram + modularity-vs-n_clusters curve** — the scalable

Keep the existing conventions: Scryfall links rather than embedded images, load saved artifacts
